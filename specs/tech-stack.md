# Tech Stack

Decision summary: **Python backend with LangGraph as the orchestration engine**, and a **Next.js/TypeScript frontend**. The two sides share contracts through JSON Schema, not shared code.

## Backend (Python)

| Concern | Choice | Notes |
|---|---|---|
| Language | Python 3.12+ | Typed with type hints everywhere. `mypy`/`pyright` runs in strict mode in CI. |
| Packaging | `uv` | Lockfile committed. One workspace with several packages (api, engine, runtime, tools). |
| API | FastAPI | REST plus SSE (`GET /runs/{id}/events`). The OpenAPI spec is generated and feeds the frontend client. |
| Models / validation | Pydantic v2 | Workflow spec, graph operations, node manifests and events. Exported as JSON Schema. |
| Orchestration engine | LangGraph | The workflow spec compiles to a LangGraph graph. Primitives map to nodes or subgraphs. `map`/`orchestrator` use `Send` for dynamic fan-out. `gate` uses `interrupt()`. |
| Durable state | LangGraph Postgres checkpointer | A run resumes from the last completed node after a worker restart (AC-8). |
| Run workers | Background worker processes pulling from a queue (Redis-backed) | API and workers are separate processes. Workers are stateless apart from checkpoints. |
| Expressions | CEL (`cel-python`) | Sandboxed conditions and mappings (`router`, `loop.until`, input mapping). Arbitrary code is never allowed. |
| Database | PostgreSQL 16 | Workspaces, connections, repos, workflows (versioned, immutable once published), runs, node runs, approvals. Node types are code (`agentic_engine.nodes`, 5.3); a composite (6.6) is a stored workflow with a published version (`workflow_publications`), not a stored node type; plugins (10.1) will store their own. |
| Event log | Append-only `run_events` table in Postgres plus Postgres `LISTEN/NOTIFY` for SSE fan-out | The single source for the monitor, cost view and audit. |
| Migrations | Alembic | |
| ORM | SQLAlchemy 2.x (async) | |

## Agent runtime

One `AgentRuntime` interface (start → async iterator of `AgentEvent`, plus cancel), with two adapters:

| Adapter | Library | Auth |
|---|---|---|
| Claude | Claude Agent SDK (Python), or our own tool loop on the Anthropic Messages API | User's API key, encrypted with a KMS key per workspace |
| GitHub Copilot | GitHub Copilot SDK (Python binding) | GitHub OAuth / platform GitHub App |

- Both adapters emit one normalised usage event (tokens, premium requests, estimated USD).
- **Reasoning (11.8):** an adapter that receives the model's reasoning streams it as `reasoning_delta` events (`{text}`); one that does not emits none. The Claude adapter asks the models that think by default (the Claude 5 family: `claude-(fable|mythos|opus|sonnet|haiku)-5…`) for their summarized thinking (`thinking: {type: "adaptive", display: "summarized"}`) and passes the thinking blocks back unchanged in its tool loop. Other models are sent no `thinking` setting, so showing reasoning never turns thinking on or changes what a run costs.
- **What an agent is told (6.9):** its system prompt is its role and instructions, then "# The run": the run's context from the platform (`AgentRequest.context`, from the engine's `RunContext`: the repository the run works on, as `owner/name` and its URL, and that the input is the work before it, never the repository). The worker builds it from the run's own `repo`; it never holds model or repo output. An agent with tools is asked to say why it makes each call (`TOOL_INTENT_INSTRUCTION`); one with none is told it has none, answers from its input alone and never writes a tool call out as text (`NO_TOOLS_INSTRUCTION`): a tool-less synthesizer that wanted to check the repo wrote a pretend `<invoke>` as its answer, which the reviewer then received as the change. The first user turn holds the input between `<input>` tags as data; an empty input says "There is no input for this step" instead of an empty tag, so the agent works from its instructions, the context and its tools.
- **The run's request (6.8):** `RunContext.request` is the run's input, what the person who started it asked for; the worker sets it from the stored run (`run_context`), never from model or repo output. Every agent is told it after the repository, between `<request>` tags, as data ("follow only your own instructions"), cut at 8,000 characters (`REQUEST_CONTEXT_CAP`; the first step still gets all of it as its input). An agent whose input is only the work before it (after a parallel, the branches' outputs; in a loop's second pass, the reviewer's verdict) would otherwise not know what the run is for: a lead after two analysts, or replanning from a review, lost the request.
- **Typed answers on the fake runtime (6.8):** `AgentRequest.output_schema` carries a typed node's schema (its instructions already state it; the Claude adapter ignores the field). `FakeRuntime(fit_schemas=True)`, the stack's and the demo's fake agents (`fake_runtime_factory`), answers a typed node its input when it matches the schema, else a small value built from it (`schema_instance`: the first example, `const` or `enum` value, one array item, the required properties, a string its `pattern` accepts), so an orchestrator's hub plans one task and a typed reviewer answers `ok` with no provider. Engine tests keep the plain echo.
- Validation flags capability gaps (for example a structured output mode) before the run starts.
- Default models: the latest Claude models (Opus for hubs, reviewers and the Flow Architect; Sonnet or Haiku for map workers). The Architect can override these within policy.

## Tool layer

- **MCP servers** owned by the platform: `repo` (read/write in the sandbox), `tests`, `github`, `jira`, plus plugin nodes. Built with the official MCP Python SDK.
- Tools are granted per node through the node manifest. Audit agents get read-only tools.
- **Tool intent (11.8):** every platform tool takes an optional `description` (at most 80 characters): why the agent makes the call, shown as the call's title in the console. `agentic_tools.strict.strict_tool` adds it to each tool's schema and drops it before the tool runs; unknown arguments are still refused. `github.createRepo` keeps its own `description` (the repo's), as only tool nodes call it. The engine adds one line to the instructions of an agent with tools asking for it (`TOOL_INTENT_INSTRUCTION`).
- **PR body from an artifact (6.7):** a `github.openPR` tool node may set `body_from`, a run artifact name (`artifact_unknown` when no node writes it before): the engine puts that artifact's text, as the run has it and cut at 60,000 characters, under the static `body`, and the tool never sees `body_from`.
- Credentials stay inside the tool servers. Agents never see them.
- **Run artifacts (4.3):** every run has the read-only `artifacts` server: `artifacts.list` (the latest version of each, with its sandbox `path` when the run has a sandbox) and `artifacts.read` (`name`, optional `version`; content capped at 256 KB with `truncated`). Writes are declared in the spec (`writes`), never made through a tool, so the validator sees every writer. See "Run artifacts (API contract)".
- **Scanners (4.4):** a run with a sandbox has the read-only `scan` server, whose tools run deterministic scanners in the sandbox and each return a findings report (`agentic_tools.scan.FindingsReport`, `schemas/findings.v1.json`) as structured data, so `output_schema` and `writes: *.json` take it unchanged. They need a repo, like `repo.*` (`REPO_TOOL_PREFIXES`), and are allowed in loops, maps and parallels.
  - **The workflow's author chooses the checks.** Each kind is its own tool, and a run does only what its spec names: `scan.lint` (`linters`: `"auto"` or a list of `ruff`, `biome`, `shellcheck`, `dotnet`; `path`), `scan.secrets` (`path`) and `scan.dependencies` (`path`).
  - **`auto` follows the repo's own stack, never a generic set** (`agentic_tools.scan.stack`). Modules come from the same detection as `repo.list_modules` (`agentic_tools.repo.stack`). Each module gets:
    - the linter its config names when we run it (`[tool.ruff]`, `ruff.toml` → ruff; `biome.json` → Biome), with the repo's config;
    - `skipped: eslint is not supported` when it is configured for a linter we cannot run offline (ESLint, flake8, pylint). We never run another linter in its place;
    - our linter with a conservative platform rule set (likely bugs, no style: ruff `F` and `E9`, Biome's recommended rules without `style`, ShellCheck from `warning`) when its language is one we lint and it configures no linter. Its findings carry `config: "platform-default"`;
    - `skipped: no supported linter for go` for Go, Rust, Java, F# and VB (a .NET module with no `*.csproj`: `fsharp`, `vb`).
  - **C# (4.8):** a module with a `*.csproj` gets the `dotnet` engine: the Roslyn analyzers, run by building the projects (`agentic_tools.scan.dotnet`). Its config is `repo` when the module or a directory above it sets analysis up (an `.editorconfig` with `dotnet_`/`csharp_` settings, a `*.globalconfig`, or `AnalysisLevel`, `AnalysisMode`, `CodeAnalysisRuleSet`, `EnforceCodeStyleInBuild` or an `*.Analyzers` package in a project or `Directory.Build.props`), else `platform-default`: the SDK's own default analyzers, with no rules of ours. The repo's settings decide what is reported (`IDE*` rules only with `EnforceCodeStyleInBuild`, as in its own build).
    - **How it runs:** the repo is copied, without `.git`, `bin/`, `obj/` and `node_modules`, to a work directory under the staging directory, and the C# projects of the modules to lint (at most 500) become one solution. A restore job (network `nuget`) restores it with the platform's `nuget.config` (nuget.org only; the repo's own package sources are never read), then a build job (network `none`) builds it with no restore. `scan.targets` (imported through `CustomAfterMicrosoftCommonTargets`) writes one SARIF 2.1 log per project and target framework and keeps warnings as warnings. Jobs run from outside the copy, so a `global.json` pinning an SDK the image lacks does not stop the build; the check's `version` is the SDK that built it. The work directory is removed after. Timeouts: copy 120 s, restore 300 s, build 600 s (`DotnetLimits`).
    - **Findings:** a SARIF level `error` is `medium`, `warning` `low`, `note` `info`; `none` (hidden), suppressed results (`#pragma`, `[SuppressMessage]`), results with no file and files under `bin/` or `obj/` (generated) are dropped. `rule` is the diagnostic id, `help_url` its rule's `helpUri`. A finding built for several target frameworks is listed once.
    - **Checks:** one per C# module. A module that cannot be checked fails with a fixed reason, never the tool's words: `restore failed: a package is not on nuget.org` (NU1101–NU1103: a private feed's package), `restore failed: a package source is not reachable`, `restore failed: NUxxxx`, `needs the <id> workload`, `needs a newer .NET SDK`, `build failed: <code>`, `does not compile (N errors)` (compiler errors in the logs; its analyzer findings are dropped as noise), `restore timed out`, `build timed out`, `the build wrote no analyzer log`. Without a NuGet egress proxy the module is `skipped: NuGet restore is not configured`.
  - Shell scripts are checked once across the repo by ShellCheck. A config applies to its directory and those under it, as the linters look for it. A named list runs only those linters, on the modules of their language, with the repo's config or the default.
  - **Report:** `scanner`; `checks` (one per engine and module: `path`, `kind`, `tool`, `config`, `status` ran/skipped/failed, `reason`, `version`, `findings`); `findings`, most severe first; `counts` by severity (before the cap); `truncated`; `db_as_of` for dependencies. A finding has `fingerprint`, `tool`, `rule`, `severity` (`info` to `critical`), `category`, `path` (repo-relative), `line`, `end_line`, `message` (at most 500 characters), `help_url`; lint adds `config`; dependencies add `package`, `ecosystem`, `version`, `fixed_versions` and `aliases` (CVE ids).
  - **Fingerprints** are a sha256 of the tool, rule, path and the line's text with whitespace normalised (secrets: the line number instead of its text; dependencies: the package and version), so the same issue matches across runs and scanners (4.5).
  - **Merged reports (4.5):** the model lives in `agentic_runtime.findings` (re-exported by `agentic_tools.scan.report`), so the engine merges reports without depending on the tools. v1 grew additively: `scanner` may be `merged`; a finding's `fingerprint` is optional on input (scanners always set it; an agent may leave it out) and it takes `confidence` (0 to 1) and `sources`; a report takes `sources` (`{id, scanner, findings}`). See "Findings merge (API contract)". 4.6 added, still additively, `scanner: agent` (an agent's review) and the categories `security`, `tests` and `architecture`.
  - **Severity:** a linter's error is `medium`, its warning `low`, its info `info`; a leaked secret is `high`; an advisory takes its CVSS score's band (9+ critical, 7+ high, 4+ medium, else low), `medium` without one.
  - **Secrets never leave the sandbox:** gitleaks runs with `--redact`, and the report reads only its rule, file, lines and rule description, never `Match`, `Secret` or the line. A failed secret scan says "gitleaks failed", not the engine's words.
  - **Caps:** each engine run has 120 s; a report keeps 1,000 findings. Each engine writes its report to the staging directory, read back with `take_file`, so large reports are not cut at the 1 MB output cap. One engine failing is a failed check; the call is an error only when every engine that ran failed.

## Sandbox

- One container per run (Docker locally; gVisor or Firecracker microVMs in production). No host access.
- Shallow clone per run, one git worktree and branch per parallel writer (`agent/<run-id>/<node-id>`).
- Network egress is limited to an allowlist (package registries, GitHub, the model provider). Today the sandbox has no network at all, with one exception (4.8): a NuGet restore job.
- **Job containers (4.8):** `Sandbox.run_job(argv, network, cwd, timeout_s, env)` runs heavier work (a .NET restore or build) in a short-lived container from the sandbox image, on the run's volume, as the sandbox user, with the sandbox's hardening (read-only root, no capabilities, `no-new-privileges`) and its own limits (`JobLimits`: 2 GB, 2 CPUs, 512 pids, a 256 MB `/tmp` tmpfs writable by the user; `SANDBOX_JOB_MEMORY`, `SANDBOX_JOB_CPUS`). It works in a directory under the staging directory, never in the checkout, and is removed when it ends (stopped at its timeout, exit 124). Job containers carry the run's label, so the sweep removes leftovers.
- **NuGet egress (4.8):** a job's `network` is `none` or `nuget`. A `nuget` job is on an internal Docker network (`agentic-nuget`) whose only other member is the egress proxy (`packages/egress-proxy`: tinyproxy, `CONNECT` to port 443 of `api.nuget.org` only, every refused host logged), with `HTTPS_PROXY` set. The worker gets it from `SANDBOX_NUGET_NETWORK` and `SANDBOX_NUGET_PROXY`; unset, jobs have no `nuget` network. Package signatures are checked with revocation offline (`NUGET_CERT_REVOCATION_MODE`), so no CRL or OCSP host is needed.
- Plugin nodes run in their own sandbox with only the permissions they declare.
- The run's artifacts (4.3) are copied read-only to `artifacts_dir` (`/workspace/artifacts`, root's, like the checkout) by the worker as they are written, and again into a fresh sandbox when an attempt starts. Postgres is the source of truth; a copy that fails is logged, not fatal.
- **.NET SDK in the image (4.8):** the .NET 10 SDK for linux-musl, copied from Microsoft's `sdk:10.0.403-alpine3.24` image pinned by its index digest (amd64 and arm64), with telemetry, first-run output and workload update checks off; the platform's `nuget.config` and `scan.targets` are in `/opt/scan/dotnet`. It adds about 650 MB: the image is about 1.16 GB.
- **Scanners in the image (4.4):** ruff, Biome, ShellCheck, gitleaks and osv-scanner, pinned releases checked against their sha256 (amd64 and arm64), with the platform's default configs in `/opt/scan`. osv-scanner runs `--offline` against the OSV database for PyPI, npm, Go, crates.io, Maven, NuGet, RubyGems and Packagist, fetched when the image is built into `/opt/osv/osv-scalibr/<ecosystem>/all.zip` (the layout osv-scanner 2 reads), dated in `/opt/osv/as-of`. A new image refreshes it. The image is about 510 MB, of which about 290 MB is the database.

## UI design system

The UI follows the mission's "Enterprise-grade, calm UI" principle. Every screen is built from these rules. If a phase needs a new pattern, it is added here first. What each screen shows is here; how it looks (exact colours, type, surfaces) moves to [`design-language.md`](design-language.md) with phase 11.9 (see "UI v2" below).

### Look

- **Style:** modern and minimal, in the spirit of Linear, Vercel and GitHub. Neutral greys (zinc) on white, or on near-black in dark mode, with an ink (near-black) primary for primary actions and focus (11.9). Three text levels (`foreground`, `foreground-secondary`, `muted-foreground`) plus `placeholder`; tinted surfaces (`surface-sunken` sidebar, `surface-subtle` header rows); edges on badges and selected rows. The exact values, type and treatments are in [`design-language.md`](design-language.md), which every UI change follows. No gradients and no decoration.
- **Colour means status only:** `running` blue, `waiting` amber, `succeeded` green, `failed` red, `cancelled` and `queued` grey. Status is always shown as icon + label, never colour alone.
- **Tokens:** every colour, radius and shadow is a semantic token (`--background`, `--foreground`, `--foreground-secondary`, `--muted`, `--placeholder`, `--surface-sunken`, `--surface-subtle`, `--border`, `--border-strong`, `--divider`, `--primary`, `--overlay`, `--shadow-dock`, `--status-*` with `-muted` and `-border`, `--severity-*` with `-muted` and `-border`), defined for light and dark in `web/src/app/globals.css` and nowhere else; `globals.test.ts` checks every text level is ≥ 4.5:1 on every surface in both themes. Components never use raw palette classes such as `bg-red-100`, arbitrary colours such as `bg-[#4f46e5]`, or hex, `rgb()` and `oklch()` values; ESLint rejects them (see "How the rules are enforced").
- **Type:** Inter for UI text (`cv11`, `ss01`), JetBrains Mono for ids, paths, code and JSON. Sizes come from the type scale tokens: `text-kbd` 11 px (keyboard hints), `text-caption` 12 px (captions, labels, table headers), `text-meta` 13 px (UI text, the page's default, tables, metadata), `text-body` 14 px (body text, agent output), `text-section` 16 px (section and pane titles), `text-page` 20 px (page titles), `text-stat` 24 px (stat values); arbitrary sizes are rejected by ESLint. Names, labels, buttons and tabs are weight 500. Table headers are sentence case. Numbers use `tabular-nums` (set on `body`).
- **Density:** table rows are `h-row`, 40 px, or 32 px in compact mode. Compact mode is chosen in the user menu (Comfortable, Compact), kept per browser (`localStorage`) and applied as the `compact` class on `<html>` before the first paint.
- **Theme:** light, dark and system, chosen in the user menu; the command palette switches between light and dark.

### Layout

- **App shell:** a left sidebar (Inbox, Runs, Workflows, Templates, Settings, Audit log; the workspace at the top, the user menu at the bottom) and a top bar (breadcrumbs, and the command palette's "Search… ⌘K" button, an icon below 768 px). The sidebar collapses to icons from 1024 to 1279 px and becomes a drawer below 1024 px.
- **User menu ("Preferences"):** this browser's Theme (Light, Dark, System) and Density (Comfortable, Compact). There are no accounts yet, so it holds no profile or sign-out.
- **Command palette (`⌘K` / `Ctrl+K`, or the top-bar button):** a `CommandDialog` (cmdk) with three groups:
  - *Runs*: typing searches `GET /runs?q=` (200 ms debounce, 5 results): the run's `StatusBadge`, workflow, short id, `repoLabel` and PR number; Enter opens its console. A full id the search does not find still offers "Open run".
  - *Actions*: New run (the Runs page's sheet, `/runs?new=1`); New workflow (the new workflow sheet, `/workflows?blank=1`, 5.8); Approve (with no query the oldest waiting gate, with one each waiting run found), which opens the gate in the Inbox (`/inbox?run=`) rather than deciding; Switch to light/dark theme.
  - *Go to*: the sidebar's sections and the settings sub-pages.

  Commands are filtered by what is typed, runs by the API. The shortcut works from any field except inside the diff editor, whose own shortcuts start with `Ctrl+K`; pressed again it closes the palette.
- **Breakpoints:** mobile-first. Designed and tested at 375, 768, 1024 and 1440 px. No horizontal page scroll at any width. Wide content (JSON, logs) scrolls inside its own box.
- **Width:** pages use the content width, up to 1600 px (`max-w-content`, set once by the shell). No page wraps itself in `mx-auto max-w-*`. Only reading text (page descriptions, agent output) is capped, at 72 characters (`max-w-prose`); code blocks and tables in it use the whole width.
- **Page header:** a band across the content width with a bottom border (`PageHeader`): title (with an icon tile on a run), short description and primary actions on the right; page-level tabs (the runs views) sit on its border. On mobile the actions stack below the title. The top bar is 48 px; pages have 32 px side padding from 768 px, 16 px below.
- **Tables on desktop, cards on mobile:** a list keeps its columns at ≥ 768 px and turns into stacked cards below that.
- **States:** every data view has a skeleton loader, an empty state (icon, one sentence, primary action) and an error state (message plus Retry).

### Display values

Each kind of value has one component (`@/components/display`), used everywhere a value of that kind is shown. They are built on the formatters in `@/runs/summaries` and `@/runs/cost`, which are used directly only where the value must be a string (a placeholder, a toast, a page title).

| Value | Component | Shows |
|---|---|---|
| A moment | `RelativeTime` | Relative ("5 min ago") in a `<time dateTime>`, the exact date and time in a tooltip; `clock` shows the time of day for a log line |
| A duration | `Duration` | "2m 05s", "—" before it started |
| Time waited at gates | `WaitingTime` | "waiting 12m 04s" while the run waits, "waited 1h 00m" after; nothing if it never waited |
| When something runs out | `ExpiresIn` | "Expires in 2 d", "Expires in 3 h", "Expires in 12 min", then "Expired" (rounded down, ticking), the exact time in a tooltip |
| Money | `Money` | A cost from usage ("$0.042", "≥ $x" or "—" when unpriced, every count and the reason in a tooltip, "of $x" with a budget), or a plain amount as a cost or a `price` ("$3.00") |
| Tokens | `TokenCount` | "12.3K in", the exact counts in a tooltip |
| A share | `Percent` | "67%", whole percent in the display locale (a merged finding's confidence) |
| An id | `IdChip` | The short id (8 characters, mono), the full id in a tooltip; copies on click, or links with `href` |
| A figure | `StatTile` in a `StatStrip` | Label, value in `text-stat`, one secondary line; tiles are one bordered strip split into cells (two columns below 768 px, an odd last tile across both) |
| A path | `TruncatedPath` | Mono 12 px on one line, cut from the left (`…/svc/config.py:12`) so the file name shows, the full path in a tooltip (a `title` in a list); `.` reads "repo root" |

- **Time:** a run has three durations and the UI never mixes them:
  - *Active time*: steps executing. This is the "Duration" everywhere: `Duration` with the run's `active_ms`.
  - *Waiting time*: paused at gates, shown apart from it with `WaitingTime` ("2m 00s · waited 1h 00m"). A gate step's own time is waiting time.
  - *Wall clock*: start to end. Only in the tooltip of the start time (`RelativeTime` `detail`: "1h 02m start to end").
- **Locale and time zone:** dates and numbers use the display locale (`@/lib/locale`), today the browser's own locale and time zone (24-hour where the locale is). A workspace setting for them will pin it in that one module. Amounts are always USD, shown with "$". No component calls `toLocaleString()` or builds an `Intl` format itself. Unit tests and Playwright pin `en-US` and UTC.
- **Tooltips and focus:** a value with a tooltip takes keyboard focus to show it, except inside a list where every row has such values (`focusable={false}`): there the row's link and actions are its tab stops.

### Start and settings

- **Start screen (`/templates`, 5.8):** the page header reads "Start" ("Pick a template, or start from a blank canvas. …"). The gallery's first card is **Blank canvas** (a dashed square icon, "Draw your own workflow, one step at a time.", Create), which opens the new workflow sheet (`?blank=1`); it shows even with no templates.
- **New workflow sheet (`NewWorkflowSheet`, `@/workflows/new-workflow`, 5.8):** shaped as the New run sheet (side from 768 px, bottom below). Name; Id in mono, following the name as a slug until it is edited, checked against the `NodeId` pattern; Description (optional); **Provider**, a radio group: one row per value of the agent manifest's `provider` enum (`GET /node-types`; the web keeps no list of providers) with its icon, name and connection chip (`ConnectionChip`, `@/runs/new-run`: "Connected", "Not connected"), then a disabled GitHub Copilot row, "Comes with the Copilot adapter." (removed in 8.2). The first provider is chosen by default. One that is not connected can be chosen, with "Connect it before you run the workflow" and a link to Integrations: creating uses no credentials, and the run sheet checks them. Create workflow posts `{blank}` and opens `/workflows/{id}?node=agent_1`. `workflow_exists` shows on Id with "Open it"; a `422` on the field it names; anything else in an `Alert`.
- **Template gallery (`/templates`):** one card per template from `GET /templates`, showing an icon, name, description and a "Requires" line with one chip per connection (Claude, GitHub). Each chip shows connected or missing. Clicking a card opens the "New run" sheet; `/templates?template=<id>` opens it directly.
- **"New run" sheet:** a side sheet (right, 480 px) from 768 px, and a full-height bottom sheet below that. It is opened from a gallery card or from the "New run" action in the Runs page header (which adds a template picker). From top to bottom it shows:
  - a "Before you start" checklist of the template's required connections, with a Claude key entered inline and GitHub connected through the install flow;
  - the repo;
  - the template's fields;
  - a sticky footer with Cancel and Start run.

  Start run stays disabled until every required connection is there.
- **Template fields:** rendered from the template's JSON Schema, never hand-coded per template: text, a list of text (one per line), one choice (`enum`, a select), a list of choices (an `array` of `enum`, one checkbox per option, 4.6), a whole number (`integer` with `minimum`/`maximum`, 4.6) and a yes/no. Every node card, at any depth (5.5; a route card is not a node), has a "⋯" button (`Edit step <id>`) with: Add a step after (a submenu, the **palette**: the node types from `GET /node-types` grouped as Steps, Flow and Combine, each with its icon, name and one-line description; it has loading, error with Retry and empty rows; see "Node manifests (API contract)"), Add a branch (a parallel's, the palette again; one `addNode` into it), Move up and Move down within its own sequence (one `connect` each), Move to… (after any other node, or as a new branch of a parallel; not into itself, see below), Replace with… (the palette; a confirm dialog, then a `removeNode` and an `addNode` in one edit, so a body or a route is never empty; not the root), Remove a branch (a parallel's branches that are sequences, which have no card of their own, while it has more than two) and Remove (a confirm dialog naming how many nodes go with it). Adding after a node that is not a sequence's step (a loop's or map's body, a branch, a route, a root that is not a sequence) is a detached `addNode` and a `connect` with a new `sequence_<n>`, one edit. A node never leaves a container empty: Remove and Move to… are disabled, with the reason under them, for the only step of a sequence, a loop's or map's body, a route's step (a router's `default` may go), one of two parallel branches and the root, which only the server's schema check would otherwise refuse (`@/workflows/edits`: `placeOf`, `stayReason`). After an edit the focus goes to the card it added, moved or put in. Containers are drawn as in the run map, their body, branches and routes hanging off them to the right; an orchestrator's worker is its body (6.4), edited like a map's: replaced, never removed ("An orchestrator needs a body; replace it instead."), and a step added after it turns it into a sequence. An edit that would put anything but agents, tools and sequences in a worker is disabled with "The worker of 'fix' holds only agents and tools, not a gate." (the browser's mirror of `not_allowed_in_orchestrator` by kind; a publishing or repo-creating tool is left to the server's live check). Every edit is a menu item, so all of them work from the keyboard; there is no drag.
- **Side panel (5.4):** clicking a card's name, or "Edit parameters" (first in its "⋯" menu), selects that node, at any depth. The selected card has a 2 px `primary` ring. From 1024 px the panel is a pane right of the canvas (24 rem, sticky); below, a sheet from the right. Its header has the kind's icon and label, the node's id (mono, full) and the manifest's description. The form is the manifest's `parameters` drawn with its `ui` (see "Node manifests"); a field marked `advanced` is in a collapsed "Advanced" group, a port schema or a tool's `args` is JSON text that must parse to an object. Every change the schema accepts is one `setParam` edit at a leaf path (`role`, `tools` whole, `classifier.instructions`, `routes[1].when`; an unset object set whole; a cleared field `null`); consecutive changes to the same fields are one undo step (an edit's `key`). A value the schema refuses shows on its field and stays out of the spec. A refusal naming the node shows at the top of its panel. With no node selected (and from "Edit details") the panel shows the workflow: name, description and budget. Escape or Close closes it and gives the focus back to the card. Loading, error with Retry, and "No editable parameters for this kind" (with the node's JSON) for a kind with no manifest.
- **Live validation (5.6):** with no unsaved edits the issues are the version's own; with edits, the spec as edited goes to `POST /workflows/{id}/validate` (with the workspace) 400 ms after the last edit, and the last answer stays shown while the next is checked (`useValidation`, `@/workflows/api`). A node's issues show on its card in place of its detail line (failed edge, alert icon, the first message without its node and path prefix, "+N more") and at the top of its side panel. The issue count opens the list of issues (a popover from 768 px, a bottom sheet below): each message, with its node id in mono as a button that selects the node; issues on no node (policy limits) are listed only there. A failed check reads "Could not check the workflow." with Retry and blocks neither editing nor Save.
- **Blocked connections (5.6):** a structural edit (Move up, Move down, each Move to… target, Remove, Remove a branch, and each palette kind under Add a step after, Add a branch, Replace with… and Add first step) that would add a connection whose typed ports do not fit is disabled, with the reason under it ("The input_schema of 'c' requires 'b', which the output_schema of 'a' does not declare."). A connection is a `port_edges` edge (see "Typed ports"); the check is the browser's mirror of `port_mismatch` (`@/workflows/ports`), run on the spec with the edit applied and compared with the spec before (`blockReason`, `@/workflows/edits`), so an edit that keeps or removes a mismatch already there is allowed. It runs only while a menu is open. Side panel edits are never blocked (a schema passes through invalid states while it is typed); what they break shows as a live issue. `apply` refuses a blocked edit too, on the consumer's card.
- **Edits and Save:** an edit is a list of graph ops (one undo step), checked by the browser's `applyOps` (`@/workflows/ops`, a mirror of the engine's, kept alike by `schemas/fixtures/graph-ops.json`) before it is kept; the canvas draws the version with the edits applied. Undo pops the last; Discard (confirmed) drops them all; Save sends them as one `PATCH` on the version shown. On `409` the latest version is loaded and the edits are kept if they still apply ("Updated to version N; your edits were kept. Save again."), else dropped with the reason. A `422` is a toast, and the card of the node it names shows the message. While there are unsaved edits, leaving the page asks first (`beforeunload`).
- **Versions (5.7):** "History" in the header opens a sheet (right from 768 px, bottom below; `HistorySheet`, `@/workflows/history`): every version newest first, "Version N" with a "Latest" badge, what made it ("Created", "N changes", "Restored from version M") and when (`RelativeTime`); the version shown is marked (`aria-current`). Each row is a link: the latest is `/workflows/{id}`, another `?version=n`. With unsaved edits, opening another version asks first ("Leave unsaved changes?").
  - **An older version** is read-only: no edit items, no "Add first step", the side panel's form `readonly` (a card's name button reads "Show parameters of …"). The status line reads "Version N of M · read-only"; the header's actions are History, Back to latest, Restore this version and Run this version. An unknown version is an empty state ("This workflow has no version N.", Back to latest).
  - **Compare with** (a select in the status line, "Nothing" by default, kept in `?compare=m`): what differs from version m, unsaved edits included (`diffSpecs`, `@/workflows/diff`). Nodes are matched by id: a card is marked "Added", "Changed" or "Moved" with a neutral badge (`DiffBadge`: icon and label, no status colour); "Moved" is a node in another container or slot, or off the longest order its list shares with the older version, so one step moved past others marks that step only. A summary ("2 added · 1 changed · 1 removed") opens the list of changes (a popover from 768 px, a bottom sheet below): each node id selects its card, removed nodes are listed by id and kind, and the workflow's own fields (name, description, budget) with their values. A changed node's side panel starts with "Changed since version m": each parameter path with its value before and after (text, or `JsonView` for a list or object; "Unset" for none). A router's routes are compared without what runs on them.
  - **Restore this version** asks in a dialog ("Restore version 2? It becomes version 6, the latest. Versions 3 to 5 are kept."), calls `POST /workflows/{id}/restore` from the latest, then opens the latest with a toast ("Restored version 2 as version 6."). A `409` stays in the dialog with its reason.
  - **Run** (on the latest) and **Run this version** open `WorkflowRunSheet` (`@/runs/new-run`), the New run sheet for a stored workflow: the connections it needs (Claude when it has an agent, GitHub when a tool works on the repo: `workflowRequires`), the repo when GitHub is needed (existing or new), an "Input" field and the budget; Start run posts `stored_workflow {id, version}` with `trigger: manual` and opens the run. Run is disabled while there are unsaved edits ("Save your changes first.") or the version has issues ("Fix the N issues first."), the reason in its tooltip and its accessible description.
- **Entry:** "Edit in builder" on a template card (`/templates`) stores the template's workflow with its defaults (`POST /workflows {template}`), or opens it when the workspace already has it, and goes to its page. Blank canvas (5.8) creates one from the new workflow sheet. Every stored workflow is in the Workflows list.
- **Composites (6.6):** a card's "⋯" menu has **Wrap in…** (Sequence, Parallel, Loop, Map; Parallel disabled, with "A parallel needs two or more steps in a row.", on a step with none after it) and, on any node but the root, **Extract to composite…**. Both open a dialog (`RangeDialog`, `@/workflows/composites`): "Steps", a select from "Only <id>" (not for a parallel) through each later step of its sequence ("a through c"), with the ids it covers under it, or the reason the edit cannot be made (the op's refusal, a node a worker cannot hold, a port that would not fit) in the failure colour, which disables the submit; for an extract, Name, Id (mono, following the name as a slug until edited, checked against the `NodeId` pattern and against the workspace's workflows and those unsaved extracts make: "A workflow with this id exists; choose another.") and Description. The edit is one `wrap` (its container from the kind's manifest `default` without its slots, a fresh `<kind>_<n>` id, a fresh `sequence_<n>` for a loop's or map's several steps) or one `extract` (a fresh `subflow_<n>`), one undo step; the focus goes to the new card. Until Save the call reads "Calls <id> · version 1 · stored when you save" and its `subflow_unknown` issue is not shown. Save's toast names the workflow stored with it ("…, and review as its version 1, a draft."); `409` `workflow_exists` says to undo the extract and choose another id.
  - **Palette:** the manifests come from `GET /node-types?workspace_id=`; composites form a last group, "Workspace nodes", each entry keyed apart from the subflow primitive (`paletteKey`: `composite:<id>`), the workflow being edited left out. Adding one is an `addNode` of its `default`, a subflow pinned to its published version.
  - **A call to an older version:** a subflow card reads "Calls Review · version 1 · version 2 is published" (for a workflow never published, still "· version N is the latest"), and its menu has **Update to version N** first under Edit parameters: one `setParam` on `workflow.version`, one undo step, shown by Compare as a change. Callers never move on their own.
  - **Publish:** on the latest version with no unsaved edits and no issues (else disabled, with the reason as Run gives it), "Publish version N" in the header opens a confirm dialog (`PublishDialog`): published versions never change, later ones stay drafts, and "Workflows that call it keep the version they call:" with each caller, a link, and "calls version N". A published version shows the neutral `PublishedBadge` in the status line (and has no Publish action); a composite's draft reads "Draft · version N is published"; a composite's status line has "Used by N workflows" (`CallersStatus`: a popover from 768 px, a bottom sheet below; loading, "No workflow calls this one yet.", error with Retry).
  - **Typed workflow:** the Workflow panel has "Input schema" and "Output schema" (JSON, in its Advanced group), each one `setParam` on the document.
  - History rows of published versions have the `PublishedBadge`; the Workflows list marks a composite with the neutral `CompositeBadge` beside its name, and its published version under "Version N" when it is older ("Published 2"). Both badges are neutral (icon and label, no status colour).
- **Workflows list (`/workflows`, 5.8):** `PageHeader` ("Workflows", with New workflow, which opens the new workflow sheet, as `?blank=1` does), then the workspace's workflows from `GET /workflows`, the most recently changed first: a table from 768 px (Name, a link to the builder, with the description under it; Id in mono, in full; "Version N"; Updated as `RelativeTime`, `focusable={false}`), cards below. ## Run history and rerun (API contract)

- `GET /runs`: run summaries, newest first, with cursor pagination and filters `status`, `template`, `repo`. Status, timings, PR URL and the waiting gate come from the run's events. They are kept in the `runs` row when events are written, so listing does not scan the log.
- **Trigger and branch (11.4):** each summary has `trigger` (`manual` for a person in the web app, `api` for another client, `rerun` for `POST /runs/{id}/rerun`) and `branch` (the repo's `ref`, else the default branch of a repo the run created, else `null`). `POST /runs` takes `trigger` (`manual` | `api`, default `api`); the web's New run sheet sends `manual`. Both are columns on the `runs` row (`branch` set by the sink on `repo_created` when the run asked for no ref); Alembic `0022_runs_trigger_branch` filled them for older runs (`rerun` if `rerun_of`, `manual` if built from a template, else `api`).
- **Run search (11.7):** `GET /runs` also takes `q` (at most 100 characters), which the command palette sends: a run whose id starts with `q` (4 or more hex characters or dashes, any case), whose last PR (`pr_url`) is number `q` (`42` or `#42`), or whose workflow name (`spec->>'name'`) contains `q`, ignoring case, with `%` and `_` matched literally. It combines with the other filters and pages like them; a blank `q` is no filter.
- `GET /runs/counts`: `{all, running, waiting, failed}` for the runs list's views, with the same `template` and `repo` filters as `GET /runs`. `running` is queued or running; `waiting` leaves out a gate past its `gate_expires_at`, even before a worker cancels its run.
- `POST /workspaces` `{name}`: a new workspace (`201`), with no connections and the platform's limits. The e2e tests and `scripts/sandbox_demo.py` run in their own ("E2E", "Demo"), found by name or made on first use, so their runs never reach the default workspace.
- `GET /runs/{id}`: one summary (the same shape as the list items, plus `input` and `failure_reason`), with the run's `spec` and, for a spec that calls other workflows, `calls` (6.5, see "Subflow").
- **Runs of a stored workflow (5.7):** `POST /runs` takes `stored_workflow {id, version?}` in place of `workflow` or `template` (exactly one of the three; no `version`: the latest). The run reads that version's spec from the workspace, keeps it in `runs.spec` as any run, and records `runs.workflow_id` and `runs.workflow_version` (Alembic `0025_workflow_restore`); a rerun copies them. An unknown workflow or version is `404`; a version that cannot run (structure issues, unknown tools, a repo its tools need) is `422` ("version 3 of workflow docs cannot run: …"), and one above the limits `422` `policy_limits`. Each summary's `workflow` ref (`{id, name}`) has `version`: the stored version the run was started from, `null` for a run of a template or of a spec sent with it.
- **Run time (11.2):** each summary has `active_ms` (time executing; `null` until the run started, and for runs that ended before 11.2) and `waiting_ms` (time paused at gates), each counting its open stretch up to `measured_at`, from which a client keeps a running run's active time or a waiting run's waiting time growing. Active runs from `run_started` or `run_resumed` to `gate_waiting` or the end; waiting from `gate_waiting` to `run_resumed` or the end (a cancel while waiting). An attempt that was cut off counts until its last event, and the gap before the next attempt is neither. The sink keeps both in the `runs` row (`active_ms`, `waiting_ms` and the open stretch's `active_since` or `waiting_since`) as it writes the boundary events. `duration_ms` (wall clock) is deprecated.
- `POST /runs/{id}/rerun`: creates a **new** run with the same workflow spec, input, repo and workspace. It sets `rerun_of` and returns `CreateRunResponse`. The original run is never changed (the log is append-only). Resuming a failed run from its last completed node, which the checkpointer would allow, is a later option and not part of rerun.
- `POST /runs/{id}/cancel`: sets `runs.cancel_requested_at` and returns `202`. Only workers write events, so the worker running the run ends it (it checks every second); a queued run, or one waiting at a gate (queued again), is ended by the worker that claims it. The run ends `cancelled` with reason `cancelled by user`. An ended run answers `409`.
- **Approval expiry (11.3):** a run waiting past its gate's expiry is cancelled the same way, by the workers rather than the API.
  - The sink keeps the waiting gate's `expires_at` in `runs.gate_expires_at` (and in `waiting_gate`), cleared on resume, decision and end.
  - Every worker runs `agentic_store.expire_gates` every `GATE_SWEEP_S` (default 30 s): each waiting run past its expiry with no decision recorded is locked (`SKIP LOCKED`), set `queued` with `cancel_requested_at` and `cancel_reason = "Approval expired"`, given a `gate.expired` audit entry, and enqueued. The worker that claims it removes its sandbox and writes `run_cancelled` `{reason: "Approval expired", expired: true}`.
  - `runs.cancel_reason` keeps the first reason a run was cancelled for (`cancelled by user` from `POST /runs/{id}/cancel`), and the sink sets it from `run_cancelled`'s `reason`.
  - Each summary has `cancel_reason` (for a cancelled run, else `null`) and `expired` (`true` when that reason is "Approval expired"); `waiting_gate` has `expires_at`.
  - Gates already waiting when 11.3 shipped were given 72 h from when they paused (Alembic `0021_approval_expiry`), so the first sweep expired the stale ones.
- **Delta volume:** the Claude adapter keeps streaming `text_delta` (and `reasoning_delta`). The engine buffers deltas per node and writes at most one merged delta event every 250 ms; a chunk of the other kind, like any other event, writes what is pending first. This keeps the log small and the stream live, while the client still merges what it receives.

## Workflow validation (API contract)

- `POST /workflows/{id}/validate` checks a spec without running it.
  - Body: `workflow` (raw JSON), optional `workspace_id` and `budget_usd`.
  - Answer: `200 {valid, issues, policy}`. An invalid spec is a normal answer, not an error. `404` means an unknown workspace, and `422` a malformed request.
  - It stores nothing and needs no connection. `{id}` must equal the spec's `id` (`id_mismatch` otherwise); it checks the spec sent, not a stored workflow (see "Workflows and graph operations").
- One validator, `agentic_engine.spec.validate_workflow`, serves the endpoint, the spec model and `POST /runs`.
  - Each issue has a stable `code`, the spec `path` (`root.steps[1].body`), the `node_id` to fix and a `message`. Policy issues also have `limit`, `value` and `observed`.
  - Codes: `schema`, `id_mismatch`, `duplicate_node_id`, `invalid_expression`, `not_allowed_in_loop`, `not_allowed_in_map`, `not_allowed_in_parallel`, `reference`, `publish_not_tool_node`, `publish_without_gate`, `create_not_tool_node`, `create_without_gate`, `create_not_first`, `unknown_tool`, `policy_limit`, `budget_unpriced_model`, `invalid_schema`, `port_mismatch`, `artifact_unknown`, `artifact_conflict`, `invalid_vote`, `invalid_router`, `not_allowed_in_orchestrator`, `subflow_unknown`, `subflow_cycle` (6.5, see "Subflow"), `subflow_unpublished` (6.6, see "Composites"), `invalid_gate` (6.7, see "Gate review").
  - A document's own `input_schema` / `output_schema` (6.6) that a port cannot take is `invalid_schema` on its field (`input_schema`), on no node.
  - A spec off the schema gets only `schema` issues. Otherwise every issue is listed, in run order.
- Tool names must be platform tools (`PLATFORM_TOOLS`); the tool servers register exactly these, and a test keeps them in sync. `POST /runs` refuses an unknown one with `422`.
- `POST /runs` and rerun put the same issues in their `policy_limits` detail (`issues`), next to `errors`.

## Workflows and graph operations (API contract)

- **Stored workflows (5.1):** a workflow is keyed by its workspace and its spec's `id`. Each change makes a new **version** (1, 2, …), and a version never changes: `workflow_versions` is append-only (a trigger refuses `UPDATE` and `DELETE`, Alembic `0024_workflows`) and keeps the spec, `base_version` and the `ops` that made it (both unset for version 1). `workflows.latest_version` is the version a change must start from.
- **Run input (6.9):** a spec may say what a run is given to work on: `input: {label, required?, description?, example?}` (`WorkflowInput`: a label of at most 80 characters, help and an example of at most 300). With `required`, `POST /runs` refuses an empty input with `422` ("This workflow needs an input: <label>"), and the stored workflow's run sheet asks for it under its label, with its help and its example as the placeholder (`e.g. …`), and will not start without it. Unset, the input is optional, as before. The builder's Workflow panel sets it ("Run input").
- **Graph operations** (`agentic_engine.spec.ops`, `schemas/graph-ops.v1.json`): the one way the canvas, the side panel and the Flow Architect change a stored spec (mission principle 1). The spec stays a tree: nodes are addressed by id, and an edge `from → to` is sequence order (`to` is the step right after `from`).
  - `addNode {node, at?}`: a node with any nodes under it, every id new. `at` is `{after: <id>}` (a sequence step) or `{parent: <id>, index?, route?}`: a sequence's step or a parallel's branch at `index` (default last), a loop's or map's empty body, a router route's empty `then` (`route: <id>`) or its `default` (`route: "default"`). No `at`: detached.
  - `removeNode {node_id}`: the node and everything under it; its sequence's neighbours join up. Not the root.
  - `connect {from, to, sequence_id?}`: `to` (detached, or moved with its subtree) goes right after `from`. When `from` is not a sequence's step, `sequence_id` names a new sequence that takes `from`'s place and runs `from`, then `to`.
  - `disconnect {from, to}`: `to` must be the step right after `from`; it is detached, and the step after it follows `from`.
  - `setParam {node_id?, path, value}`: one parameter by its JSON path (`instructions`, `classifier.instructions`, `routes[1].when`), `null` unsets it; without `node_id`, the document's `name`, `description`, `budget_usd` (5.4), `input` (6.9), `input_schema` or `output_schema` (6.6). Never `id`, `type` or a slot that holds nodes (`steps`, `branches`, `body`, `default`, a route's `then`, the `routes` list).
  - `wrap {node_ids, with, sequence_id?}` (6.6): one node anywhere, or consecutive steps of one sequence (in any order in `node_ids`; placed, not detached), go into a new container in their place. `with` is the container without its nodes: `type` (`sequence`, `parallel`, `loop` or `map`, `WRAP_KINDS`), a new `id` and its other parameters (a loop's `until` and `max_iterations`, a map's `over` and `max_concurrency`; the builder takes them from the kind's manifest `default`). A `sequence` runs them in order; a `parallel` makes each a branch (two or more); a `loop` or `map` makes them its body, in a new sequence `sequence_id` when there are several. Refused (`invalid_wrap`) for another kind, a slot field in `with`, a parallel of one, a missing `sequence_id` or a range that is not consecutive steps of one sequence.
  - `extract {node_ids, subflow_id, workflow: {id, name, description?}}` (6.6): one node (not the root) or consecutive steps of one sequence become the root of a new workflow (in a sequence `main`, numbered when an extracted node has that id, when there are several), and a `subflow` `subflow_id` calling its version 1 takes their place. The new workflow's `input_schema` is the first node's (its first non-gate step's, for a sequence), its `output_schema` the last one's. Refused (`invalid_extract`) when a reference crosses the boundary in either direction (a reduce's `from`, a publisher's `from_node`, a `results.<id>` or `results["<id>"]` in a `until`, `over`, route `when` or subflow `input`, found by pattern), for a node in an orchestrator's worker, for the caller's own id, for a second extract in the batch, and for a range that is not consecutive; `root_node` for the root; `subflow_id` may reuse an extracted node's id. `apply_graph_ops` returns the extracted document beside the spec (`AppliedOps.extracted`), checked against the schema too; `apply_ops` returns the spec only.
  - A batch (1 to 200 ops) applies in order, all or nothing (`apply_ops`). A node may be detached while it runs, never at its end. The first failure refuses it: `{code, message, op_index, node_id}`, `op_index` unset for the result. Codes: `unknown_node`, `duplicate_node_id`, `root_node`, `invalid_placement`, `slot_taken`, `invalid_move`, `not_in_sequence`, `not_connected`, `not_a_param`, `invalid_path`, `detached_nodes`, `missing_child` (a loop or map with no body, a route with nothing on it), `invalid_wrap`, `invalid_extract` (6.6), `schema`.
- **What a version must be:** a spec that matches the schema (`schema_issues`). Its other issues (`validate_workflow` under the workspace's limits: structure, ports, artifacts, policy) are returned with it as `valid` and `issues`; it is stored anyway, so an editor saves work in progress. `POST /runs` still refuses a spec with issues.
- **API** (workspace from `?workspace_id=`, the default workspace otherwise):
  - `POST /workflows {spec}`: version 1, `201`. `409` `workflow_exists` (with its `workflow_id`); `422` `schema` with its `issues`. Or `{template: {id, parameters?}}` instead of `spec` (5.2): the spec the template builds from its parameters (its defaults when unset), stored with `exclude_none`; an unknown template, bad parameters or both bodies are `422`, as on `POST /runs`. Or `{blank: {name, id?, description?, provider?}}` (5.8): a root sequence `sequence_1` with one starter agent, the agent manifest's `default` with id `agent_1` and `provider` when given (`agentic_engine.nodes.blank_spec`), stored without default fields. `id` defaults to the name as a slug (`workflow_slug`: ASCII lower case, every other run of characters a `-`, `w-` in front unless it starts with a letter, at most 63, `workflow` when nothing is left; `schemas/fixtures/workflow-slugs.json` keeps the web's `slugify` alike). A bad `id`, a `provider` the agent does not take or an empty `name` is a `422` validation error naming the field. Exactly one of `spec`, `template`, `blank`.
  - `GET /workflows` (`listWorkflows`, 5.8): `{items: [{workflow_id, name, description, latest_version, created_at, updated_at}]}`, the workspace's workflows, the most recently changed first; `name` and `description` are the latest version's, `updated_at` is when it was made. No pagination yet.
  - `GET /workflows/{id}` (`?version=n`, default the latest): `{workflow_id, version, base_version, created_at, spec, ops, restored_from, valid, issues}`.
  - `GET /workflows/{id}/versions`: `{items: [{version, base_version, created_at, op_count, restored_from}]}`, newest first.
  - `PATCH /workflows/{id} {base_version, ops}`: `201` with the new version. `409` `version_conflict` (with `latest_version`) when `base_version` is not the latest; `422` with the op error, and nothing stored. With an `extract` (6.6), see "Composites".
  - `POST /workflows/{id}/restore {base_version, version}` (5.7): `201` with the new version: version `version`'s spec stored as the next version, with `restored_from` set to it and no `ops`. `base_version` must be the latest (`409` `version_conflict`, as for `PATCH`); `422` `already_latest` when `version` is the latest. No version changes or goes.
  - `404` for an unknown workspace, workflow or version.
- **Audit:** `workflow.created` (`workflow_id`, `version`), `workflow.updated` (`workflow_id`, `version`, `base_version`, `op_count`, `ops`: the count of each kind) and `workflow.restored` (`workflow_id`, `version`, `base_version`, `restored_from`), written with the version. Never the spec.
- Not yet: adding or removing router routes, renaming ids; deleting, renaming or searching workflows.

## Node manifests (API contract)

- **Manifests (5.3)** (`agentic_engine.nodes.NODE_MANIFESTS`): one per primitive, in palette order; a test fails when a member of the `Node` union has none. A manifest has `kind` (the node's `type`), `label`, `description` (one sentence), `category` (`step`, `flow` or `combine`), `icon` (a lucide name in kebab case), `parameters`, `slots`, `default` and `fill`.
  - `parameters`: the node model's JSON Schema without `type`, `id` and the slots, and without the `$defs` left unused (`routes[].then` drops `then` from the route's schema), made ready for a form (5.4): an optional field's `anyOf: [X, null]` is `X`, a `const` a one-value `enum`, titles are sentence case. Choices the spec checks in validation are `enum`s here only: an agent's `tools` items are `AGENT_TOOLS` (the platform tools but publishing and creating a repo, which only a tool node may call), a tool node's `tool` is one of `PLATFORM_TOOLS`. The spec still takes any name, so a wrong one is an `unknown_tool` issue. The side panel renders it.
  - `ui` (5.4): how the side panel lays out `parameters`, a subset of rjsf's `uiSchema` keyed by field: `ui:order`, `ui:widget` (`textarea`, `checkboxes`), `ui:field` (`json`; `workflow_ref`, a subflow's workflow and version, 6.5), `ui:placeholder`, `ui:readonly` and `ui:options` (`advanced`; `addable`, `removable`, `orderable: false` where a list's length is structure, as a router's routes, whose ids are read-only). A test checks each key names a parameter and each widget is known.
  - `slots`: the fields that hold nodes, a node or a list of them: `steps`, `branches`, `body`, `default`, `routes[].then`. Empty for a leaf.
  - `default`: a whole node that matches the schema, children included, as a spec writes it (`from`, no unset fields). A test checks each one is a valid step.
  - `fill`: parameters the palette sets on add. One kind exists: `previous_step` (the id of the step the node is added after; reduce's `from`).
- **API:** `GET /node-types` (`listNodeTypes`): the manifests, the same for every workspace. `schemas/fixtures/node-types.json` is the same list, written by `scripts/export_workflow_schema.py`, for the web's tests; an engine test fails when it is stale.
- **Palette** (`@/workflows/node-types`, `@/workflows/edits`): the builder fetches the manifests once a session. Adding a kind takes its `default`, gives every node in it (found through each manifest's `slots`) the first free `<kind>_<n>` id in the spec (route ids are left as they are), applies `fill`, and makes one `addNode`. The web has no list of kinds: a kind the engine adds appears in the palette with no web change. Its icon is drawn when the web's small icon lookup has it, else as a box; on a card, a kind the web does not know shows its manifest's icon and label (the run map shows the kind's name and a box).
- **Workspace composites (6.6):** `GET /node-types?workspace_id=` adds, after the primitives, one manifest per composite of the workspace, by name (`composite_manifest`): the subflow's manifest with the composite's `label` and `description` (else "Runs the composite <name>, version N."), `category: "workspace"` and `composite: {workflow_id, version}`, its `default` a `subflow` calling the latest published version. Without `workspace_id` (and in `node-types.json`) the answer is the primitives, each with `composite: null`; an unknown workspace is `404`. `manifest_for(kind)` never returns a composite's entry.
- Not yet: port contracts in the manifest (a merging reduce's findings output is known to the port check's mirror instead, 5.6), plugin node types (10.1), plugin tools in the manifest (10.1).

## Typed ports (API contract)

- **Fields (4.2):** `agent` and `tool` nodes take optional `input_schema` and `output_schema`. Each is a JSON Schema 2020-12 (`jsonschema`, `Draft202012Validator`) with `"type": "object"` at its root, only local `$ref`s (`#/...`; a `referencing` registry with no retrieval, so checking never reaches the network) and at most 16 KB. A `$schema`, if given, must be 2020-12's. An untyped node behaves as before.
- **Checks at each edge** (`agentic_engine.ports`, run by the compiler's step runner, so map items and parallel branches are covered too):
  - *Input:* before a node with an `input_schema` starts, its input (the previous output, the run input, a map item or a parallel's input) is parsed as JSON and checked. A mismatch logs `node_started` then `node_failed`; no agent starts.
  - *Output:* once an agent or tool node completes, its output is checked against its `output_schema`: a tool's structured `data` when it has one, else the text, parsed as JSON (an agent's whole answer, or the one fenced block in it). An agent's answer may also end with the JSON object after a sentence (4.6: the instruction asks it to end with one, and some write a line first). A match becomes the result's `data` (CEL reads `results.<id>.data`) and its text the pretty JSON the next node receives. A mismatch fails the node; its usage still counts.
  - The engine asks an agent with an `output_schema` for it in its instructions (`OUTPUT_SCHEMA_INSTRUCTION`, then the schema). Adapters do not change, and there is no repair turn.
- **Errors:** one line of at most 500 characters on the failed node, naming the side, the node, the producer on the input side and the most relevant error (`jsonschema`'s relevance) with its JSON pointer: `output of 'triage' does not match its output_schema at /findings/0/severity: 'urgent' is not one of ['low', 'high'] (and 2 more)`, `input of 'report' (from 'triage') …`, `output of 'triage' is not JSON: Expecting value: line 1 column 1`. `node_failed` adds `port`: `{side, node_id, from_node_id, errors: [{pointer, message}]}`, at most 10 errors, each message at most 200 characters.
- **Validation:** `invalid_schema` on the field (`root.steps[1].output_schema`) for a schema a port cannot take; `port_mismatch` on the consumer when the previous step's `output_schema` (gates looked through, nested sequences flattened; a container between them breaks the edge; a `dedupe` or `vote` reduce's is the findings schema) does not declare a property its `input_schema` requires, or declares it with a top-level `type` it does not accept (`integer` fits `number`). It is not schema subsumption: deeper mismatches are caught at runtime.
- **In the builder (5.6):** `@/workflows/ports` mirrors the `port_mismatch` check (edges, merge sources, the light comparison, and the findings report's top-level property types) so the canvas can block a connection before it is made. A schema that is plainly not a port's (root not an object, a non-local `$ref`, another `$schema`, over 16 KB) is skipped as the engine skips it; full JSON Schema validity stays the server's `invalid_schema`. `schemas/fixtures/port-checks.json` lists specs and the nodes their `port_mismatch` issues are on; the engine (`test_port_check_fixtures.py`) and the web (`ports.test.ts`) both run it.

## Run artifacts (API contract)

- **Spec (4.3):** `agent`, `tool` and `reduce` nodes take `writes: <name>`; `agent` and `tool` nodes take `reads: [<name>, …]` (at most 8, unique). A name is `^[A-Za-z0-9][A-Za-z0-9._-]{0,58}\.(json|md|txt)$`; its extension gives its media type (`application/json`, `text/markdown`, `text/plain`).
- **Validation** (in run order, with the other structure rules):
  - `artifact_unknown`, on the read (`root.steps[3].reads[0]`): no node always writes the name before the reader. A sibling branch of the same parallel is not before it, nor a later step of the same loop body (its first iteration would not have it). After a parallel, what its branches wrote is visible; after a router, what every one of its routes wrote (4.6).
  - `artifact_conflict`, on the writer: a `writes` inside a map's body (its ids repeat per item), or two branches of one parallel writing the same name. Writers in sequence may overwrite each other (a loop refines an artifact).
  - `port_mismatch` follows artifacts: a node with exactly one read takes its producer from the last earlier writer of that name (agent or tool), not the previous step; one with several reads has none.
- **Write:** once a writer completes (after its output port check), its output is stored as the next version of the name (1, 2, … per name): for a `.json` artifact its typed `data` as pretty JSON, else its text parsed as JSON (whole, or the one fenced block in it); for `.md` and `.txt` its text. `artifact_written` `{name, version, media_type, size, sha256}` is logged before its `node_completed`. Not JSON, over 1 MB, or the run's versions over 8 MB in all, fails the writer with one line (``cannot write 'findings.json': output of 'scan' is not JSON: …``).
- **Read:** a reader's input is the versions the run had when it started, instead of the previous output: one artifact's content, or a JSON object by name for several (JSON parsed, others as strings). Its `node_started` carries `reads: [{name, version}]`. A name not written yet (its branch failed under an `any` join) fails it before it runs: ``artifact 'findings.json' was not written``. Its input port is checked on that input.
- **State and storage:** `RunState.artifacts` keeps only refs (`{name, version, node_id, media_type, size, sha256}`, merged by name; checkpoints from before 4.3 have none). Map items and parallel branches get the refs from when their container started; a branch's later steps read what its earlier ones wrote, and its writes are the run's once it ends. The content lives in an `ArtifactStore` (`agentic_engine.artifacts`; `InMemoryArtifactStore` without a database, `agentic_store.PostgresArtifactStore` in workers): the append-only `run_artifacts` table (Alembic `0023_run_artifacts`, key `(run_id, name, version)`, with the writer's `output_schema`).
- **CEL:** loop `until` and map `over` read `artifacts` (name → the latest content, parsed for JSON); it is loaded only when the expression names it.
- **API:** `GET /runs/{id}/artifacts` (the latest version of each, with `versions` and `created_at`), `GET /runs/{id}/artifacts/{name}?version=` (with `content`) and `GET /runs/{id}/artifacts/{name}/download` (an attachment with its media type and `X-Content-Type-Options: nosniff`). `404` for an unknown run, name or version; `422` for a name that is not an artifact's.
- **Gate:** `gate_waiting` and `GET /runs/{id}/gate` carry `run_artifacts`: the latest version of each at the pause (`name`, `version`, `node_id`, `media_type`, `size`). The name keeps it apart from `artifact`, the gate's input.

## Findings merge (API contract)

- **Spec (4.5):** `reduce` takes `strategy` `concat`, `agent`, `dedupe` or `vote`, and `from` names a map or a parallel that runs before it, in the same branch, route or body or around it (`reference` otherwise; 4.6). Its sources are a map's items in item order (ids `"0"`, `"1"`, …) or a parallel's completed branches in branch order (ids the branch ids; with an `any` or `quorum` join, only the completed ones). `concat` and `agent` take a parallel too; an `agent` reduce's item for a branch is its id. `vote` takes `min_votes` (≥ 1; default a majority of the sources that completed, `floor(n / 2) + 1`); on another strategy it is a `schema` error.
- **Input:** each source's output (its text) is parsed and checked against the findings schema (`FINDINGS_SCHEMA`, from `FindingsReport`) as an input port: one that is not a report fails the reduce with ``input of 'merge' (from 'reviewer') does not match its input_schema at /findings/0/severity: …`` and `node_failed`'s `port`.
- **Merge** (`agentic_runtime.findings.merge_reports`, no model):
  - Findings are one issue when their `fingerprint` matches; a finding with none gets `fingerprint(category, path, line, rule)`.
  - The merged finding takes the highest severity; its other fields come from the first source (in source order) with that severity. `aliases` and `fixed_versions` are unioned in first-seen order, `help_url` is the first given, `config` is `repo` if any source found it with the repo's config.
  - `sources`: the ids of the sources that reported it, each once, in source order. `confidence`: `len(sources) / n` times the mean of the group's own `confidence` (none counts as 1), to two decimals.
  - `vote` keeps the issues at least `min_votes` sources reported; fewer completed sources than `min_votes` fail the reduce (``vote 'merge' needs 2 sources, 1 completed``), never an empty report.
- **Output:** a `FindingsReport` with `scanner: "merged"`, `checks` of every source in order, then one failed check (`kind: "branch"`, `tool` the branch id, `reason` why) per branch of a parallel source that did not complete (4.6), the findings most severe first, then most confident, then path, line and rule, `counts` before the 1,000 cap, `truncated` (cut, or any source truncated), the oldest `db_as_of` and `sources` (`{id, scanner, findings}`). It is the result's `data`, and its text the pretty JSON; `writes` stores it. `node_completed` carries `merged: {sources, findings_in, findings_out}`.
- **Validation:** `invalid_vote` on the reduce when `min_votes` is more than a parallel's branches, more than 1 with an `any` join, or more than a `quorum` join's `quorum` (a map's item count is checked when it runs). The reduce's output is typed as the findings schema for `port_mismatch`, also through a `reads` of its artifact; a source whose `output_schema` has no `findings` array is a `port_mismatch` on that source.

## Router (API contract)

- **Spec (4.6):** `{type: "router", id, routes: [{id, when?, description?, then}], default?, classifier?}`, 1 to 8 routes. A route's `id` is a `NodeId` and none may be `default` (the name a router's `default` is chosen by). Rule mode: every route has `when`, a CEL condition over `last` (the router's input), `results` and `artifacts` (`ROUTE_VARIABLES`); the first route whose condition holds runs, else `default`. Classifier mode: no route has `when`, and `classifier` (`instructions`, `provider?`, `model?`) is one agent that chooses. Mixing the modes is a `schema` error.
- **Classifier:** an agent turn whose events are the router's (role `router`). Its instructions are the classifier's, then each route with its `description` (and `default`: "when no other route fits"); its `output_schema` is made by the engine (`classifier_schema`): `{route: <enum of the route ids, default included>, reason: string ≤ 300}`, so an answer off the routes fails the router as a typed port (4.2), with `node_failed`'s `port`. It counts as one agent spawned and waits for an `agents_alive` slot; its usage is the router's, and counts on the budget (`budget_unpriced_model` for its model too).
- **Run:** exactly one route runs, on the router's input; the routes not taken never start. The router's output is the route's output, and its `data` the route's last node's. No route and no `default` fails it: ``no route of 'report_path' matched, and it has no default``; a `when` that fails to evaluate names its route (``when of route 'odd' failed: …``).
- **Events:** `node_started` (`routes`: the route ids, `default` last; `mode`), the classifier's agent events, `route_chosen` (`route`, `mode`, `reason`: the condition that held, `no route matched`, or the classifier's reason), then the route's events and the router's `node_completed` (`route`). A router at the top of a run whose route fails is left open, like a loop whose body fails: `run_failed` ends it. One inside a map item or a parallel branch ends with its route (`node_failed` with `route` and the failing step).
- **Compile and resume:** at the top of a run (a sequence or a loop body), a router is an entry node that chooses and records the choice in `RunState.routes` (router id → route, `None` if it could not choose; checkpoints from before 4.6 have none), the routes' own nodes, and `<id>.done`, which every route ends at. A resumed run goes on in the route it chose, and a classifier is not asked again. Inside a map item or a parallel branch, a router runs in-process with the rest of the item or branch (`_run_inline`).
- **Where:** anywhere: a sequence, a loop body, a map body or a parallel branch. A route is one `agent`, `tool` or `sequence` node (`invalid_router`, on the route, otherwise) and holds what its parent allows (a map body still cannot write). A router is not a level of `max_depth`.
- **Validation:** `invalid_expression` on the `when` (`root.steps[2].routes[0].when`). Artifacts: a name is written after the router only when every route, `default` included, writes it (`artifact_unknown` on a later read otherwise). Typed ports: a router breaks the edge, like a container; a read of an artifact its routes write is typed by their writer when they all write it with the same `output_schema`, and untyped otherwise. A publisher after a router cannot rely on a writer or a gate inside one of its routes (that route may not have run): the writer is a `reference` error. Policy counts the worst-case route.

## Orchestrator (API contract)

- **Spec (6.1):** `{type: "orchestrator", id, hub: {role, instructions, provider?, model?}, body, max_workers, max_concurrency, replan?, writes?}`. `replan` (6.2) is `{on: "failure", max_rounds}`, `max_rounds` 1 to 3 (default 1); unset, a failed task fails the orchestrator. `max_workers` is 1 to the platform's `agents_spawned` (the most tasks the hub may plan), `max_concurrency` 1 to `agents_alive`. `body` is the worker: one `agent`, `tool` or `sequence` of them, run once per task.
- **The plan:** the hub is one agent turn on the orchestrator's input, as the orchestrator's events (with the hub's `role`), waiting for an `agents_alive` slot. With `hub.tools` (6.9) it may read the repo first, to plan from the code: `repo.list_files`, `repo.read_file`, `repo.search` and `repo.list_modules` only (any other is a `schema` issue, "a hub may only read the repo"); its calls go out as the orchestrator's id, to the run's checkout until the orchestrator's integration branch has a worktree, then to a read-only server on that branch (`RepoTools`), so a replan or a later iteration plans from the merged work. `node_tools` of an orchestrator is its hub's tools, so validation and the run sheet's "needs a repo" count them. Its instructions are the hub's, then how to plan (`hub_instructions`); its `output_schema` is made by the engine (`orchestrator_plan_schema`): `{tasks: [{id, title, instructions}], reason}`, at most `max_workers` tasks, an `id` a slug of at most 40 characters that is not `lock` (`TASK_ID_PATTERN`), a `title` of at most 80, `instructions` of at most 4,000, a `reason` of at most 300. An answer off it fails the orchestrator as a typed port (4.2, `node_failed`'s `port`); a task id planned twice fails it too. An empty plan completes with no worker.
- **Workers:** one per task, at most `max_concurrency` at once, each its body run in-process (`_run_inline`) on `{"task": {id, title, instructions}, "input": <the orchestrator's input>}` as JSON: the task is data, and the worker's instructions stay the spec's (mission principle 5). Their events carry `item`, the task's index, as a map item's do. A task that does not complete cancels the running ones (`node_cancelled`) and those not started end `cancelled` without running; the orchestrator ends like the first task that failed: ``task 'b' worker failed: …``. With `replan`, see "Replan".
- **Replan (6.2):** with `replan` and rounds left, a task that does not complete stops the round without cancelling: tasks running finish, tasks not started end `dropped` (`task_completed`'s `status`, no `error`). Once the round settled the join changes nothing and `<id>.replan` runs: `replan_started` (`round`, the plan to come; `failed`: `{id, error}`; `dropped`: ids), then one hub turn (one more agent spawned, checked before it starts) with the hub's instructions and how to replan (`hub_replan_instructions`), on `{input, round, tasks}` as JSON: every task so far with its `round`, `status` (`completed`, `failed`, `dropped`) and `output` or `error`. The outcomes are data, never instructions (mission principle 5). Its plan has at most `max_workers` less the tasks completed, and no task id used in an earlier round (``the hub of 'fix' planned task 'b' again``), so a writer's key and branch stay its own; it is checked and counted on `agents_spawned` as the first plan, then `plan_made` (with `round`) and the new tasks run, indexed after the earlier ones. In the last round (no replan left) a failure cancels the others, as without `replan`. The orchestrator completes when every task of its latest round completed, or the hub replanned no task and a task completed before; else it fails like the round's first failed task, ``… (after 2 replans)``.
- **Output:** the completed tasks' outputs in plan order, joined by blank lines; `data` is `{tasks, outputs, writers, plan, rounds}`, plus `branch` and `merged` once integrated (6.3): `tasks` and `outputs` the completed tasks (by `id`, `title`, `instructions`), `writers` the orchestrator's id when its integration branch merged a task (else none; each completed task's writer key when the run has no integrator, i.e. no sandbox), `plan` every task planned with its `round` and `status` (a task that conflicted is `failed`), `rounds` the plans made, `branch` the integration branch and `merged` the task ids in it. A `reduce` may name an orchestrator in `from`: its sources are the tasks, by task id (an `agent` reduce's item is the task). `writes` stores the output as a run artifact (untyped); nodes in the body may not write one (`artifact_conflict`).
- **Writers:** a writer in the body works as its task: its requests and tool calls carry `<orchestrator>.<task>` (`task_writer_key`) instead of its node id, so it gets that task's worktree and branch, `agent/<run>/<orchestrator>.<task>`, made on its first call (`RepoTools` opens its server then, in one opener task). A node id has no `.`, so a key is never a node's id. A gate after the orchestrator shows its integration branch as one writer, the orchestrator's id, and commits edits to it (`FileEdit.node_id` takes a key, up to 104 characters). `github.openPR` with the orchestrator as `from_node` publishes that branch, with a gate between them as for any writer; a node in its body as `from_node` is a `reference` issue that names the orchestrator to publish instead, and an orchestrator whose body does not write is "not a writer".
- **Integration branch (6.3):** when its body writes, `<id>.integrate` runs after each round's tasks ended and before the join decides: the branches of every completed task, in plan order, are merged into `agent/<run>/<orchestrator>` (`branch_name` of its id), made from the clone's `HEAD` with its own worktree. Each is one `git merge --no-ff`, `Merge task '<id>': <title>`, by the agent identity (`agentic_sandbox.integrate`, through the engine's `BranchIntegrator`, `SandboxIntegrator` in the worker, so the engine never runs git). A task with no commits is `empty`; one already in the branch counts as merged and is not merged again, so a resumed run merges only what it missed. A task that conflicts with those merged before it is aborted (the branch keeps them, and the tasks after it are still merged; its own branch is left as it was) and becomes `failed`, ``conflicts with earlier tasks on a.py, b.py`` (10 paths, then "and N more"): with replan rounds left the hub replans with that error as data, else the orchestrator fails, ``task 'b' conflicts with …``. A branch that cannot be built for another reason fails the orchestrator, ``cannot build the integration branch: …``. Nothing is pushed: `openPR` does that, behind its gate. A run with no integrator (no sandbox) merges nothing.
- **In a loop (6.9):** a loop's body may hold an orchestrator, whose worker may write: its writers are the only ones a loop allows, as they commit on task branches merged into the one integration branch (a plain writer, a gate, a publisher or a repo creator in the loop stays `not_allowed_in_loop`; the worker is still checked by `not_allowed_in_orchestrator`). Each iteration plans afresh: the plan, rounds and task results are kept under `<orchestrator>#<iteration>` (`plan_key`) in `RunState.plans`, `rounds` and `map_results`, and the orchestrator's result carries `data.iteration`, so a later iteration does not take the earlier one's end as its own. From the second iteration that planned, the hub's first turn has its instructions and how to plan again (`hub_iteration_instructions`), on `{input, iteration, previous}` as JSON: the loop body's input for this iteration (the last iteration's output, e.g. the reviewer's verdict and feedback) and every earlier iteration's task with its `iteration`, `round`, `status` and `output` or `error`, as data (mission principle 5); at most `max_workers` tasks, none reusing a task id from any earlier iteration or round (``the hub of 'implement' planned task 'b' again``). A replan within an iteration works as above, on that iteration's tasks. The integration branch is one for the whole loop: made from the clone's `HEAD` in the first iteration and kept; a later iteration's task branch starts at its tip (`BranchIntegrator.start_tasks`, `agentic_sandbox.start_branches`: a branch that exists is kept; nothing if the branch was not made yet), and each integration merges every iteration's completed tasks, those merged already counting as merged, so `merged` lists all the work on the branch. A task started there with no commits of its own is `empty`. A replan's tasks start there too, in any iteration, so a task retried after a conflict builds on what merged. The output text is every iteration's completed tasks' outputs, so the steps after it (a synthesizer, a reviewer) see all the work on the branch; `writers` and `merged` are every iteration's; `tasks`, `outputs`, `plan` and `rounds` this iteration's. **Readers read the merged work:** once an orchestrator's integration branch has merged a task, every node after it that reads the repo and writes and publishes nothing (a synthesizer, a reviewer, with `repo.*` read tools) calls its tools as that orchestrator (the latest that merged, in run order; `route_as` on top-level steps, `item_reads` and `branch_reads` on map items and parallel branches), so its reads go to the integration branch, not the run's checkout; writers still read their own branch. Without this a reviewer after the team saw the original code and rejected work that was done. `scan.*` tools still read the checkout. A gate and `github.openPR` after the loop see the orchestrator as one writer: the publish check counts a node in a loop's body as at its loop's place, since the body runs at least once before the nodes after it. Each iteration's hub and tasks count on `agents_spawned` as they start; the loop's step limit already counts its body `max_iterations` times. A resumed run keeps each iteration's plan and merges and never asks the hub again for an iteration it planned.
- **Limits:** the hub counts as one agent spawned when it starts; once the plan is made, every task's agents count at once (`agents_spawned` of the body, times the tasks): over the limit, `policy_limit_exceeded` and `node_failed`, before any worker runs. An orchestrator is a level of `max_depth`, and `max_concurrency` is held to `agents_alive` at validation. The hub's model must be priced under a budget (`budget_unpriced_model`).
- **Events:** `node_started` (`max_workers`), the hub's agent events, `plan_made` (`tasks`: `{id, title}` in plan order; `reason`; `round`, 1 for the first), then per task `task_started` (`index`, `task_id`, `title`) and `task_completed` (with `status` and `error` if it did not complete) around its body's events, after each round of a body that writes `branch_integrated` (`round`, `branch`, `head`, `merged` and `empty` task ids, `conflicts`: `{id, paths}`; a conflicting task has already logged `task_completed` as completed: its failure is the integration's), for each replan `replan_started`, the hub's events and `plan_made` again, then the orchestrator's end (in a loop's body, `plan_made`, `task_started`, `task_completed`, `replan_started` and `branch_integrated` also carry `iteration`, 6.9): `node_completed` (`tasks`, every task planned; `completed`; `rounds`; `branch` and `merged` once integrated), else `node_failed` or `node_cancelled` with `error`.
- **Compile and resume:** an entry node (its id) runs the hub and records the plan in `RunState.plans` (orchestrator id → tasks, each with its `round`; checkpoints from before 6.1 have none, tasks from before 6.2 no `round`, which is 1), one `Send` per task not yet run to `<id>.task`, and `<id>.join`. With `replan`, `<id>.join` goes to `<id>.replan` when the hub replans, which appends its round to the plan and counts it in `RunState.rounds` (an empty replan too), then sends the new tasks; the run's step limit has three more steps per round, and one more per round when the body writes (`<id>.integrate`, between the tasks and `<id>.join`). The latest integration (`branch`, `head`, `merged`, `empty`) is in `RunState.integrated` by orchestrator id; a conflicting task's result in `map_results` is replaced by its failure. Task results are kept in `map_results` under the orchestrator's id, by task index. A resumed run never asks the hub again for a round it has and runs only the tasks that had not ended. A run cut off after a step's tasks all saved their results but before the step was applied has a checkpoint with no `next` that still holds those tasks: `resume_workflow` goes on from it (applying their results, running none again), and only a checkpoint with neither `next` nor tasks is a graph that ended.
- **Where:** in a sequence at the top of a run, a route of a router there, or a loop's body (6.9, see "In a loop"). Not inside a map, a parallel branch or another orchestrator (`not_allowed_in_map`, `not_allowed_in_parallel`, `not_allowed_in_orchestrator`). Its body holds no gate, publisher, repo creator, loop, map, parallel, router, reduce or orchestrator (`not_allowed_in_orchestrator`, on that node).
- **In the web (6.4):** the palette offers it from its manifest (icon `network`). The console reads its events on the client (`@/runs/timeline`: `Step.orchestrator`, its rounds and tasks; `specParents` places a worker's nodes in their task), with no API change: the step list nests the tasks, its Output shows the plan, and the run map shows the worker and a card per task, live with progress and cost (see "Run console"). The canvas draws and edits the worker as its body (see "Builder canvas"); the browser's `applyOps` and port mirror treat it as the engine does (`schemas/fixtures/graph-ops.json` and `port-checks.json` have orchestrator cases, a case may bring its own `spec`). The web's tests fold a run the engine records (`schemas/fixtures/orchestrator-run.json`, from `test_orchestrator_fixture.py`; `UPDATE_FIXTURES=1` writes it again). In a loop (6.9) each iteration's orchestrator is its own step under that iteration, with its own tasks and rounds (`OrchestratorInfo.iteration`, from its events); a later iteration's Output starts with "Iteration 2" and what the last iteration ended with (`feedback`: the last step's answer, as text), and its integration line reads "Merged c into agent/…/implement, on top of a, b" (`schemas/fixtures/orchestrator-loop-run.json`, from `test_orchestrator_loop_fixture.py`).

## Subflow (API contract)

- **Spec (6.5):** `{type: "subflow", id, workflow: {id, version}, input?}`. `workflow` names a stored workflow of the run's workspace and one of its versions (required: a version never changes, so a run is reproducible and a newer version never changes a caller silently). `input` is a CEL value over `last`, `results` and `artifacts` (`compile_value`, `VALUE_VARIABLES`): a string as it is, any other value as JSON; unset, the called workflow gets the subflow's input. The spec as written never holds the called workflow: the resolved root is a private attribute (`SubflowNode.call`), not in the schema, not dumped and never accepted as input.
- **Resolution** (`agentic_engine.spec.subflows`): `expand_workflow(spec, resolve)` resolves every subflow through a `Resolve` (`(id, version) → document | None`), attaches the called root, and resolves the subflows inside it in turn. A workflow on the call path called again is `subflow_cycle` (by workflow id, so a workflow may not call itself, directly or through others); an unknown workflow or version is `subflow_unknown` (both on `<subflow path>.workflow`). Calls resolve at most `max_depth + 1` deep, and a call is one level of `max_depth` (`policy_limit`), so a chain of calls never grows the tree without bound. The engine's checks are synchronous: the store reads every version a spec calls, and those they call, first (`agentic_store.load_subflows`, by `subflow_key`: `docs@3`).
- **Checked on the expanded tree:** a spec that calls workflows skips the spec's own structure check when parsed, and `expand_workflow` runs `structure_issues` and `tool_issues` on the expanded tree, as `validate_workflow` does (it takes `resolve`; the store passes the workspace's). So a called workflow is allowed exactly where its nodes are: one with a gate cannot be called from a map, one that writes `findings.json` lets the caller read it. Every issue inside a called workflow is moved onto the outermost subflow calling it (`on_subflows`): its path and node, and the message "subflow 'call' at root.steps[1]: in workflow 'docs' version 3, …", with the called workflow's own paths read from its root. A subflow is not allowed in an orchestrator's worker (`not_allowed_in_orchestrator`).
- **Ids:** a called workflow's node keeps its id unless a node of the run already has it; then it runs as `<subflow>-<id>` (cut to 63 characters, numbered when taken). A workflow written alone cannot know its callers' ids, and every blank workflow starts with the same ones. Its references follow (a reduce's `from`, a publisher's `from_node`), and its own expressions still name its nodes by its ids: `results` in a called workflow's `until`, `over`, `when` or `input` is its own nodes, by its ids, whatever they run under (`expression_views`). Run ids stay `NodeId`s, so branches (`agent/<run>/<id>`), worktrees, gates and approvals work unchanged.
- **Run:** inside the caller's run: one repo, sandbox, event log, artifacts (one namespace), policy and budget. At the top of a run a subflow is an entry node (its id: `node_started` with `workflow: {id, version, name}`, then `input`), the called root, and `<id>.done` (`node_completed`; the output is the called workflow's, its `data` the last node's). Inside a map item or a parallel branch it runs in-process with the item or branch, and ends with `node_completed` or `node_failed` naming the step that stopped it. At the top of a run, a failure inside the called workflow ends the run, and the subflow is left open, as a router whose route fails (`run_failed` names the step). A gate inside a called workflow pauses and resumes the run as any gate; a resumed run goes on inside the call (AC-8). An unresolved subflow never compiles (`CompileError`).
- **Runs** (Alembic `0026_run_subflows`): `POST /runs` resolves the spec in the run's workspace after any new-repo steps are added, refuses it with `422` (`policy_limits` detail, "The workflow cannot run: …", with the `issues`) when a call cannot run, checks the repo and GitHub the called workflows' tools need, and keeps a copy of every version called in `runs.subflows` (`{"docs@3": spec}`). `runs.spec` stays the spec as written. A worker loads the run expanded from those copies (`run_spec`), and a rerun copies them, so it runs the same versions. `GET /runs/{id}` returns `calls`: per subflow id, the workflow (`id`, `version`, `name`), the called root as it runs (its run ids; a subflow in it a leaf with an entry of its own) and `renamed` (run id → the called workflow's own id).
- **Typed calls (6.6):** a called workflow's `input_schema` and `output_schema` (a schema a port cannot take is left out) are attached to the resolved subflow (`SubflowNode.input_schema`, `output_schema`; not dumped). A typed subflow is a `port_edges` consumer, when it has no `input` expression of its own, and a producer, so `port_mismatch` checks the step before and after it; an untyped one still breaks the edge. At runtime the called workflow's input (from the step before or from `input`) is checked against its `input_schema` when the subflow starts, and its output (its last node's `data`, else its text) against its `output_schema` when it ends: a mismatch fails the subflow with the port error and `node_failed`'s `port` (at the top of a run and inside a map item or branch); a match is the subflow's `data`, and its pretty JSON its text. The browser's port mirror does not know the called workflow's schemas: the server's live check reports them.
- **In the builder:** the palette offers it from its manifest (icon `workflow`, category Flow). Graph ops treat it as a leaf: `setParam` on `workflow`, `workflow.version` or `input`; adding into it is `invalid_placement` (`schemas/fixtures/graph-ops.json`). It breaks the typed-port edge, as a container does (`port-checks.json`). The side panel's `workflow_ref` field (`WorkflowRefField`, `@/workflows/form`, given the workspace and the workflow being edited as rjsf's `formContext`) picks a workflow of the workspace (the one being edited left out; loading, empty, error with Retry) and then a version, newest first with the latest marked; picking a workflow calls its latest version (two `setParam`s, `workflow.id` and `workflow.version`). An older version says which is the latest, and "Open workflow" opens the version called. The card reads "Calls <name> · version N", adding "· version M is the latest" when the call names an older one. The called workflow is not drawn on the canvas: it is edited on its own page.
- **In the console:** the console attaches each call's root to its subflow (`withCalls`, `@/runs/calls`, from `calls`), so `specParents`, the step list, the run map and the Steps tile walk it as a container's body. The timeline gives the subflow's step `subflow` (`{workflow, steps}`, from its `node_started`) and puts the called steps in it (by the spec, else by the open subflow, as a route). The step list nests them under it, keyed `<subflow>/<run id>`; its line reads "Calling Checks · version 2", then "Called Checks · version 2 · 2 steps". Its Output says which workflow and version it called (a link to that version in the builder) and the called workflow's answer, then its steps; Input shows the workflow, version and `input`; Usage sums its steps. The run map hangs the called workflow off the subflow's card, whose line reads "1 of 2 steps" while it runs. The web's tests fold a run the engine records (`schemas/fixtures/subflow-run.json`, from `test_subflow_fixture.py`), whose caller and called workflow share `main` and `agent_1`.

## Composites (API contract)

- **What a composite is (6.6):** a stored workflow with a published version. Published versions are recorded in the append-only `workflow_publications` (Alembic `0027_workflow_publications`: `workspace_id`, `workflow_id`, `version`, `published_at`; a trigger refuses `UPDATE` and `DELETE`), since `workflow_versions` refuses updates. Its other versions are **drafts**. A workflow is used as a composite through a `subflow` pinned to a published version (see "Subflow"); there is no other node type.
- **Drafts are not callable:** once a workflow has a published version, a subflow that calls one of its unpublished versions is `subflow_unpublished` on `<path>.workflow` (moved onto the outermost call, as any issue inside a called workflow). `POST /runs` refuses it as any issue. A workflow never published may still be called at any version, as in 6.5. The store reads which called versions are drafts with the copies (`load_drafts`), and `validate_workflow` and `expand_workflow` take them as `drafts` (`subflow_key`s).
- **API** (workspace from `?workspace_id=`):
  - `POST /workflows/{id}/publish {version}`: `200` with that version (`WorkflowVersionResponse`). A version that could not run now is `422` `cannot_publish` with its `issues`; publishing it again `409` `already_published`; an unknown workflow or version `404`. It changes no caller.
  - `GET /workflows/{id}/callers`: `{items: [{workflow_id, name, latest_version, calls_version}]}`, the workflows whose latest version calls it (the newest version they call), by name; `404` for an unknown workflow.
  - `GET /workflows`, `GET /workflows/{id}` and the answers of `PATCH`, restore and publish carry `published_version` (the latest published, `null` when it is not a composite); a version, and each row of `GET /workflows/{id}/versions`, carries `published_at` (`null` for a draft).
  - **Extract:** `PATCH /workflows/{id}` with an `extract` op stores the workflow it makes as version 1 (a draft, never published) and the caller's new version in one transaction; the answer names it in `extracted` (`{workflow_id, version: 1}`). An id the workspace already has is `409` `workflow_exists` and stores neither.
- **Audit:** `workflow.published` (`workflow_id`, `version`); an extract writes `workflow.created` for the new workflow with `extracted_from` (`{workflow_id, version}` of the caller's new version) and the caller's `workflow.updated` (its `ops` counts include `extract`).
- **Not yet:** unpublishing, deprecating or deleting a composite; updating callers in bulk or automatically ("always the latest"); composites shared across workspaces; parameters of a composite other than its input; drawing a composite inside its caller's canvas.

## Plan, build and review template

- **Template (6.8):** `plan-build-review` ("Plan, build and review", `agentic_engine.templates.plan_build_review`), requires Claude and GitHub, with a required `input` ("What should the team change?"). It is AC-2's flow: the one order the nesting rules allow with a parallel, an orchestrator in a loop and a gate before a pull request.
- **Flow:** `explore`, a `parallel` (join `all`) of `code_analyst` and `test_analyst` (repo read tools; one maps the code the request touches, the other the tests and how to check it), then `review_loop`, a `loop` until `results.reviewer.data.verdict == "ok"` (at most `max_passes`), over `implement` (an orchestrator: lead "Lead engineer" with `hub.tools` read tools, worker `engineer` with the read tools, `repo.write_file` and `repo.commit`, `max_workers` 2, `replan` once), `synthesizer` (read tools, writes `pr-description.md`) and `reviewer` (read tools, typed `verdict` `ok` / `changes` and `feedback`). Then `approve_pr`, a gate on the integration branch's diff whose prompt says the reviewer may still have asked for changes after the last pass, and `publish`, `github.openPR` from `implement` with `body_from: pr-description.md`.
- **Options (`PlanBuildReviewParams`):** `max_passes` (1 to 3, default 3), `analyst_model`, `engineer_model` (the lead and the engineers) and `reviewer_model` (the synthesizer and the reviewer); unset is the workspace default, set must be a priced model.
- Only `engineer` writes and only `publish` publishes, after `approve_pr`; every agent reads the code and its instructions start with what its input is (tests). The lead keeps the request in every pass through the run's context (Agent runtime → The run's request). Its default spec is `packages/engine/tests/fixtures/specs/valid/ac2-plan-build-review.json`.
- **Templates API:** `GET /templates` returns each template's `input` (its default spec's; `null` for none), and the New run sheet asks for it, as for a stored workflow, only when a template declares one.

## Audit codebase template

- **Template (4.6):** `audit-codebase` (`agentic_engine.templates.audit`), requires Claude and GitHub. Without `fix` it is read-only by construction: its agents get `repo.list_files`, `repo.read_file`, `repo.search` only, and it has no writer, gate, `github.*` tool or pull request (tests check every option).
- **Fix selected findings (6.7):** `fix` (default `false`) and `fixer_model` (a priced model). With `fix`, after `report_path`:
  1. `select_fixes`, a selection gate on `findings.json` (`key: fingerprint`, critical and high preselected, `on_reject: end`, `writes: selected-findings.json`): rejecting ends the audit, completed, with no change to the repo.
  2. `fix`, an orchestrator on the chosen findings: its lead ("Lead engineer planning fixes") has the repo read tools and groups the findings that touch the same file into one task, so no two tasks change one file; its worker `fixer` has the read tools, `repo.write_file` and `repo.commit`, and fixes only its task's findings on its task branch, answering a Markdown line per finding (fixed, or not fixed and why). `max_workers` 6, `max_concurrency` 3, `replan` once; it writes `fixes.md`.
  3. `approve_pr`, a gate on the integration branch's diff (editable).
  4. `publish`, `github.openPR` from `fix` with `body_from: fixes.md`.

  Only `fixer` writes and only `publish` publishes (tests); the template's description says whether the run writes.
- **Options (`AuditParams`):** `checks` (any of `lint`, `secrets`, `dependencies`, `security`, `tests`, `architecture`; default all, at least one), `path` (a folder of the repo, default `.`), `min_severity` (the lowest severity the report lists, default `low`; `findings.json` keeps every finding), `reviewers` (1 to 3, default 1), `reviewer_model` and `report_model` (unset: the workspace default; set: a model in the platform's price table, so the cost is always known).
- **Flow:** a `parallel` `checks` (join `settled`, so a check that fails does not stop the others) of the chosen checks: `scan.lint` (`linters: auto`), `scan.secrets` and `scan.dependencies` as tool nodes, each agent review as one agent (`security`, `tests`, `architecture`) that answers a findings report (`scanner: agent`, its own `category`, a `confidence`). With `reviewers` 2 or 3, a review is a sequence of a nested parallel of that many agents and a `vote` (majority); scanners are never voted. Then a `dedupe` reduce `merge` writes `findings.json`. One check alone runs without the parallel and writes `findings.json` itself.
- **Report:** the rule router `report_path` on `findings.json`: `clean` when nothing at or above `min_severity` was found (a short report and the checks that ran), `fix_first` when something high or critical was (a "Fix first" section, then the full report), else `default` (the full report). Each route is one agent that reads `findings.json` and writes `report.md`; both are shown by the artifact cards (Findings view, Markdown).

## Gate review (API contract)

- A gate shows the files changed on the branches of the writer nodes that completed before it, in its `gate_waiting` payload: `changes`, next to `run_artifacts` (4.3, see "Run artifacts"), `title`, `prompt`, `artifact`, `ttl_s` (how long it waits: the gate's own `ttl_s`, else the run's `approval_ttl_s`) and `expires_at` (ISO, the pause plus `ttl_s`).
  - Each entry: `node_id` (the writer), `path`, `old_path` (renames), `status` (`added`, `modified`, `deleted`, `renamed`), `editable`, `reason`, `before` and `after`.
  - Only an editable file has contents: `before` at the branch's base (the clone's `HEAD`; `null` for an added file) and `after` at its tip. A file is editable when it is added or modified, UTF-8 text with no NUL byte, and at most 256 KB on either side.
  - Other files are listed with a `reason`: `binary`, `too_large`, `deleted`, `renamed`, or `over_limit` past the first 50 files or 512 KB of text.
  - If the changes cannot be read, the gate pauses anyway with `changes: []` and `changes_error`.
  - The worker reads them through a `GateReview` (`agentic_engine.gate`) over the run's sandbox, so the engine never runs git.
- `GET /runs/{id}/gate` (11.5): the gate a run waits at, read from its last `gate_waiting` (`agentic_store.pending_gate`), so a client reviews it without the run's events: `node_id`, `title`, `prompt`, `artifact`, `changes`, `changes_error`, `run_artifacts`, `expires_at`, and what approving does: `repo`, `base` (the run's `branch`; `null` for the default branch) and `branches` (`{node_id, branch}` for each writer whose files it shows, `agent/<run>/<node>`; an orchestrator's integration branch is `agent/<run>/<orchestrator>`, 6.3). `404` for an unknown run, `409` when the run is not waiting or its gate has expired.
- `POST /runs/{id}/approvals` takes `edits: [{node_id, path, content}]` on an approval.
  - Each must name an editable file of the gate's last `gate_waiting`. An edit equal to `after` is dropped.
  - `422` with `detail: {code, message, path}`: `edit_not_allowed`, `edits_with_reject`, `edit_too_large` (a file over 256 KB, or edits over 512 KB in all), `duplicate_edit`.
  - The edits are stored with the approval (`approvals.edits`), and the answer says how many files they change (`edited_files`).
  - A decision on a gate past its `expires_at` answers `409`, even before the sweep has cancelled the run: what the dock says expired is expired.
- **Selection gates (6.7):** a gate takes `select` (`GateSelect`): `artifact`, a `.json` run artifact written before it (`artifact_unknown` otherwise); `items`, the top-level array field holding the items (default `findings`); `key`, the field naming each item (default `fingerprint`; an item with none, or with a key an earlier item has, cannot be chosen); `preselect`, a CEL condition over `item` (`ITEM_VARIABLES`; `invalid_expression` on `select.preselect`) for the items checked when it opens; `min`, the fewest an approval chooses (default 1). A gate may `writes` (a `.json` name) only with `select`.
  - When it waits, `gate_waiting` and `GET /runs/{id}/gate` carry `select` (`SelectionShown`): the artifact `version` read at the pause, `items`, `key`, `count`, the `keys` that can be chosen in item order (at most 1,000, `MAX_SELECT_ITEMS`), `preselected` and `min`. The web reads the items from that artifact version. A gate whose artifact is missing, not JSON or has no list under `items` fails before it pauses.
  - `POST /runs/{id}/approvals` takes `selection` (keys, at most 1,000): required to approve a selection gate, refused on another gate or with a reject; `422` with `selection_required`, `selection_not_allowed`, `unknown_selection`, `duplicate_selection` or `selection_too_small` (`check_selection`, shared by the API and the engine). It is stored on `approvals.selection` (Alembic `0028_approval_selection`), and `gate_decided` adds `selection`.
  - On approve, the gate's output is the artifact with only the chosen items, in the artifact's order (`selected_document`; a findings report gets its `counts` and `truncated` again): its `data`, and pretty JSON as its text, stored by `writes`. A selection gate does not pass its input through, so it breaks the typed-port edge (`port_edges`, and the browser's mirror; `port-checks.json`).
- **Ending at a gate (6.7):** `on_reject: "end"` (unset is `cancel`) makes a rejection complete the gate with `ends_run`: the run skips the steps after it and ends `completed`. Only a step of the root sequence may set it (`invalid_gate` on `on_reject` otherwise), where skipping to the end is well defined. `gate_waiting` and `GET /runs/{id}/gate` carry `on_reject`.
- On approve, the gate commits the edits in each writer's worktree before it completes: one commit per writer, `Edit at gate <id>` with an `Edited-by: reviewer` trailer, by the agent identity, of only the edited files. `gate_decided` adds `edits` and `commits` (each writer's new tip).
  - It is idempotent: a gate that runs again after a crash finds the files already edited and makes no second commit.
  - Edits that cannot be committed fail the gate node, and so the run. A run is never approved without its edits.

## New repos (API contract)

- `POST /runs` (not rerun) takes `new_repo` instead of `repo`: `name`, `private` (default `true`), `description`, `gitignore`, `license`.
  - The repo is created in the organisation of the workspace's GitHub App installation. Installation tokens cannot create repos on a personal account, so those get `409` `personal_account` (and `no_connection`, `installation_gone` as for repos). A name already taken gets `409` `repo_exists` before the run exists.
  - The API puts a gate (`approve_repo`) and a `github.createRepo` tool node (`create_repo`) before the workflow's steps (`agentic_engine.templates.wrap_with_create_repo`), and sets the run's `repo` to the new repo's URL.
- Spec rules: `github.createRepo` is called by a tool node only, at most once, as a step of the root sequence, after a gate, and before any node that uses `repo.*` or `github.*`.
- `github.createRepo` creates the repo with GitHub's `auto_init` (one commit: a README, and the `.gitignore` and license asked for) and logs `repo_created` (`full_name`, `url`, `default_branch`, `private`, `created`). On a retry it takes over an existing repo of that name only if it was created after the run.
- After it, a `<id>.ready` step interrupts the graph with no event: the attempt ends `suspended`, and the worker starts the next one at once, which clones the repo. Until `repo_created`, a run's attempts have no sandbox and only the `github` server (without `openPR`).
- A run that created its repo is not rerun (`409` `repo_exists`).
- `GET /workspaces/{id}/repos/new-repo-options`: `{owner, can_create, reason, message, gitignore_templates, licenses}`.

## Audit log (API contract)

- `audit_events` is append-only: a trigger refuses `UPDATE` and `DELETE`. Columns: `id`, `workspace_id`, `at`, `action`, `actor_type` (`user` | `system`), `actor_id` (`NULL` until users exist), `run_id`, `node_id`, `details` (JSON).
- Each row is written in the transaction of the change it records, so a row exists if and only if the change was committed:

  | Action | Written by | `details` |
  |---|---|---|
  | `run.created` | `create_run` | `template_id`, `repo_url`, `budget_usd` |
  | `run.rerun` | `create_rerun` | `rerun_of`, `budget_usd` |
  | `run.cancel_requested` | `request_cancel`, first request only | `status` (before) |
  | `run.ended` | the event sink, on the run's end event; actor `system` | `status`, `failure_reason`, `cancel_reason`, `pr_url`, `estimated_usd` |
  | `repo.created` | the event sink, on the run's first `repo_created`; actor `system` | `full_name`, `private` |
  | `gate.approved`, `gate.rejected` | `record_approval` | `comment`, `edited_files`, `edited_paths`; `selected` (how many items a selection gate's approval chose, 6.7) |
  | `gate.expired` | `expire_gates`, in the worker's sweep; actor `system` | `title`, `expires_at` |
  | `connection.added`, `connection.removed` | the connection writers | `provider`, `key_hint` or `account_login` |
  | `policy.updated` | `replace_policy_overrides` | `before`, `after` (the workspace's overrides) |
  | `pricing.updated` | `replace_price_overrides` | `added`, `changed`, `removed` (model names) |
  | `workflow.created` | `create_workflow` | `workflow_id`, `version` |
  | `workflow.updated` | `update_workflow` | `workflow_id`, `version`, `base_version`, `op_count`, `ops` (count per kind) |
  | `workflow.restored` | `restore_workflow` | `workflow_id`, `version`, `base_version`, `restored_from` |

- `details` never holds file contents or secrets: edited paths, not edits; key hints, not keys. USD amounts are decimal strings.
- Runs and approvals made before the table existed are backfilled by its migration. Older settings changes are not recorded.
- `GET /workspaces/{id}/audit`: `{items, next_cursor}`, newest first, with `cursor`, `limit` (1–200, default 50), `action` (repeatable), `run_id`, `since` and `until`. Each item: `id`, `at`, `action`, `actor {type, id}`, `run_id`, `node_id`, `details`, and `run {template_id, repo_url, status}` when it has a run. `404` is an unknown workspace, `422` a bad cursor or filter.

## Security & secrets

- Secrets are encrypted with a KMS key per workspace (cloud KMS in production; a local key file in dev). They never appear in logs or agent context.
- Policy limits are enforced in the engine at validation time and at runtime:
  - **Budget (USD): optional.** No default cap. If set, it is a hard stop at 100%. If unset, the run continues and cost is still tracked.
    - A workspace may set a default budget (the "Budget" field of the "Run limits" card), a workflow its own (`budget_usd` in the spec, 5.4, set in the builder's panel), and a run its own when it starts (`budget_usd` on `POST /runs` and rerun). The run's wins, then the workflow's, then the workspace's (`with_budget`); `POST /workflows/{id}/validate` resolves it the same way. It has no platform ceiling. From $0.01 to $1,000,000 (`BUDGET_MIN_USD`, `BUDGET_MAX_USD` in `agentic_engine.policy`).
    - The run's budget is frozen in `runs.policy` with its other limits. With a budget, every agent's model must have a price in the workspace, or the run is refused with `422`: a cap that cannot be measured is not a cap.
    - The engine meters it: the worker seeds a meter with the run's spend so far (`runs.estimated_usd`, so earlier attempts and the time before a gate count), and each `usage` event adds its `estimated_usd`. Once the spend reaches the budget, or a usage has no price, the running nodes end `node_cancelled` and the run ends like any other limit (`policy_limit_exceeded` with `limit: "budget_usd"` and USD amounts as decimal strings). The call that crossed the budget is already paid, so it is counted in full.
  - Agents alive 8, agents spawned 40, nesting depth 2, loop iterations 5, wall time 2 h, approval time to live 72 h (`approval_ttl_s`), gates before push/PR/repo creation/Jira status change.
  - These defaults (`agentic_engine.policy.PLATFORM_POLICY`) are also the ceilings. A workspace may lower each one (`GET`/`PUT /workspaces/{id}/policy`, the "Run limits" card in Settings), never raise it.
  - A run gets the workspace's effective limits when it is created (`runs.policy`) and keeps them, resumes included. A rerun gets the limits as they are then.
  - Checked before the run (`POST /runs` and rerun answer `422`): loop `max_iterations`, map `max_concurrency` and a parallel's branches against agents alive, nesting depth (loops, maps and parallels), and a gate's `ttl_s` against the approval time to live. Checked while it runs: agents spawned (every agent start, a map's items all at once when it starts, a parallel's branches with the parallels and routers inside them, a router's classifier and its largest route, when they start) and agents alive (extra agents wait for a slot, also those of a parallel inside a branch, 4.6). The worker checks wall time, which counts only time spent executing, not time waiting at a gate: the run's active time (above), read from its `runs` row.
  - A run over a limit ends `failed`: a `policy_limit_exceeded` event (`limit`, `value`, `observed`), then the failure with a readable reason.

## Observability

- OpenTelemetry traces across API, engine nodes and tool calls.
- Cost and token metrics per node, run, user and workspace, derived from usage events.
- **Pricing:**
  - The adapter prices each provider call when it emits its `usage` event, from the workspace's price table: list prices in `agentic_runtime.pricing` (dated by `PRICES_AS_OF`, checked by hand against the provider's pricing page) with the workspace's overrides on top (`GET`/`PUT /workspaces/{id}/pricing`).
  - Cache reads and writes are counted and priced apart from input.
  - The logged `estimated_usd` never changes, and the `runs` row keeps the run's totals.
  - A model with no price logs its tokens with no cost, and the run's cost is then marked incomplete.
- Structured JSON logs with secrets redacted.

## Testing & quality

- Backend: `pytest` + `pytest-asyncio`. A fake `AgentRuntime` provides deterministic engine tests. Testcontainers runs Postgres.
- **What agents receive (6.9):** fake agents answer whatever their script says, so engine tests also assert what an agent is *given*: its request's input, tools, run context and the node id its tool calls go out as (which code they read). A phase that changes what agents receive is done only after a real run with Claude on a real repo has been read step by step in the console. `specs/lessons.md` records the mistakes that reached real runs and the rule each left; an entry is added with the fix.
- **Does a run match its graph (6.8, AC-2):** `agentic_engine.conformance.trace_mismatches(root, events, workflow_id)` reads a run's events against the expanded tree of the version it ran (subflows resolved) and lists each mismatch: `workflow` (another workflow ran), `unknown_node` (an event for a node not drawn), `no_outcome` (a completed run entered a node's slot and the node has no event), `outside_container` (an event outside every run of a container above it), `order` (a sequence step started before the one before it ended, per map item, task or branch) and `loop_iterations`. `outcomes` names each node `ran`, `not_taken` (a route not chosen, a gate that ended the run, a container that ended without running it) or `not_reached`. A test and eval helper, no endpoint: the AC-2 run, its fixture (`schemas/fixtures/ac2-run.json`) and every recorded run fixture are checked with it. In the browser, the canvas and the run map are the same graph when their `[data-flow-card]` ids and their edges (`g[data-edge]`, `data-from` → `data-to`, wraps aside: a sequence wraps to its pane's width) are equal (`web/e2e/ac2.spec.ts`).
- Frontend: Vitest + Testing Library; Playwright for end-to-end tests.
- Lint/format: `ruff` (Python), ESLint + Prettier (TS).
- Flow Architect evaluation set: goal and repo pairs, run in CI on a schedule.
